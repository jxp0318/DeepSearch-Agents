# 技术设计记录（ADR）

> 本文档记录 deepsearch-agents 的关键技术决策：为什么这么做、放弃了什么方案。
> 每条决策都按「背景 → 决策 → 放弃方案 → 理由」四段记录，便于回溯取舍过程。

## ADR-001 反思循环：外层 Python 循环，不改框架

**背景**：deepsearch 类系统的核心是「搜索 → 反思信息是否充分 → 针对缺口补搜」。deepagents 框架只提供单次规划执行（planning → task 调度 → 汇总），没有信息充分性评估和迭代补搜机制。

**决策**：在 `run_deep_agent` 外层包一个反思循环，不 fork、不修改 deepagents 源码：

```text
for round in 1..MAX_ROUNDS:
    main_agent.astream(消息, thread_id)      # 复用同一条 thread，agent 自带上文
    ↓ 本轮最终回答 + token 消耗
    评估器（独立 LLM 结构化调用）
    ↓ SufficiencyEvaluation{sufficient, missing_dimensions, follow_up_queries}
    sufficient / 预算耗尽 → 终止，输出最后一轮结果
    不充分 → 把缺口维度 + 补充查询拼成新消息，进入下一轮
```

**放弃的方案**：
1. ~~改写主智能体 system_prompt，让模型自己反思~~——本质是提示词工程，循环不可控、无法强制预算约束，无法体现工程设计能力
2. ~~fork deepagents 在图内加反思节点~~——耦合框架内部结构，升级即碎；且上下文隔离机制（`_EXCLUDED_STATE_KEYS`）会让图内反思节点拿不到完整子智能体中间产物
3. ~~LangGraph 外面再套一层 graph~~——多一层抽象无实际收益，Python 循环已足够清晰

**为什么这个位置可行（源码依据）**：
- `create_deep_agent` 返回 LangGraph `CompiledStateGraph`，`checkpointer + thread_id` 持久化全部消息状态——同一 thread_id 二次 invoke，模型天然看到第一轮全部内容（`graph.py` L708-729）
- 子智能体经 `task` 工具调用，结果以 ToolMessage 回流主循环（`middleware/subagents.py`），外层循环拿最终 AIMessage 即可，无需感知内部结构

**终止条件（三选一）**：
1. 评估器判定 `sufficient=true`
2. 达到最大轮数 `REFLECTION_MAX_ROUNDS`（默认 3）
3. 累计 token 超预算 `REFLECTION_TOKEN_BUDGET`（默认 150k，取自 AIMessage.usage_metadata，无元数据时按字符数估算）

**成本权衡**：每轮多一次评估器 LLM 调用（输入=问题+本轮答案，输出=结构化 JSON，约 1k token）。换来的是可量化的质量提升（评测数据见 `app/eval/eval.md`，阶段四产出）。

## ADR-002 评估器与执行模型复用同一 model 实例

**背景**：反思评估器需要 LLM 做结构化输出。

**决策**：复用 `app/agent/llm.py` 的 `model`，但**不使用默认的 json_schema 结构化输出**，改为 `model.with_structured_output(SufficiencyEvaluation, method="json_mode")`，并保留纯文本 + 宽容 JSON 解析作为回退。

**理由**：
- 评估任务是轻量判断任务，不值得引入第二个模型配置
- 结构化输出保证 `missing_dimensions` / `follow_up_queries` 是可枚举的列表，可直接拼进补搜消息，不依赖文本解析
- **实测踩坑**：默认的 `json_schema` 方式在部分 OpenAI 兼容端点上直接返回 `400 This response_format type is unavailable now`。这个异常被降级逻辑吞掉后表现为「每轮都判定信息充分」，反思循环静默失效——**看起来在跑，其实永远不补搜**。改用兼容性更好的 `json_object` 模式后恢复正常

**三层兜底**（评估器故障不应让整个任务失败）：
1. `json_mode` 结构化输出（首次失败后置位标记，后续轮次不再重试，省一次无谓请求）
2. 纯文本调用 + 宽容 JSON 解析（剥 Markdown 围栏、截取首尾花括号、兼容布尔写成字符串）
3. 仍失败 → 判定「已充分」终止循环，保留本轮结果，并在 `reasoning` 里记下异常

**放弃的方案**：~~用便宜的小模型做评估器~~——合理方向，但当前只有一套 API 配置；待阶段四评测时若发现评估器成本占比显著，再引入分级模型（记为 TODO）。

## ADR-003 中间轮结果与最终结果的推送语义分离

**背景**：前端以 `task_result` 事件作为任务结束信号（`useDeepAgentSession.ts`），若反思循环的每轮都发 `task_result`，前端会提前结束。

**决策**：事件分级——
- `round_result`：每轮执行结果，前端仅展示在时间线
- `reflection_evaluation`：评估器结论（充分/不充分 + 缺口 + 理由）
- `reflection_supplement`：进入补搜轮，附补充查询列表
- `task_result`：仅整个反思循环结束后发送最终结果

这组事件本身也是产品能力的可视化：用户在时间线上能看到「搜了 → 反思 → 不够 → 再搜」的思考链。

## ADR-004 执行事件的投递模型：多连接广播 + 事件缓冲回放

**背景**：现象是「后端日志显示任务已经跑完，页面却一直停在生成中」，刷新也不一定恢复。定位过程与结论：

1. **写探针实测后端投递链路**——起独立服务、挂 WebSocket 客户端、POST 任务，确认事件确实发得出去，排除「后端没推」
2. 定位到两个投递层缺陷，且都与「页面收不到事件」直接对应：
   - `active_connections` 用 `thread_id → 单个 WebSocket` 存连接。前端 thread_id 存在 localStorage，**同一浏览器的多个标签页共享同一个 thread_id**，后建连的页面会把先建连的覆盖掉，事件只发给最后一个页面，其余页面永远空白
   - **事件即发即弃，没有缓冲**。页面刷新、断线重连、或 WebSocket 假死（对端进程被 `--reload` 重启，浏览器侧 TCP 未及时感知，以为还连着）时，错过的事件永久丢失，前端只能靠下一次任务重置

**决策**：把投递层从「单连接、即发即弃」改成「广播 + 可回放」：

```text
active_connections: dict[thread_id, set[WebSocket]]   # 一个 thread 允许多个页面
每个事件分配 seq（thread 内自增）并写入该 thread 的环形缓冲（默认 200 条 / 最多 50 个 thread）
emit  → 入缓冲（无论有没有连接）→ 广播给该 thread 下所有连接，发送失败的连接就地剔除
WS 建连 → 先回放该 thread 的缓冲事件，再接收新事件
begin_task() → 新任务开始时清空缓冲，避免回放到上一轮任务的轨迹
前端 → 按 seq 去重（seq <= 已处理最大值则丢弃），刷新/重连后补齐但不重复
```

**为什么缓冲放在后端而不是前端**：真实状态源在后端。前端重连后无法「问」后端要历史，除非后端存了。放在后端还有一个副作用是好的——**任务跑完后才打开的页面也能看到完整执行轨迹**，这在演示完整执行链路时特别有用。

**放弃的方案**：
1. ~~只改前端去重~~——治不了根因，事件在前端根本收不到
2. ~~用 Redis Pub/Sub 或消息队列存事件~~——单进程教学项目引入外部依赖，收益不匹配；缓冲上限写死 200 条已够覆盖一次研搜轨迹（进程重启后缓冲即失效，这是刻意的取舍，与阶段三的持久化 checkpointer 是两件事）
3. ~~给每个标签页单独分配连接键~~——会让「任务绑定的 thread_id」和「连接键」分裂成两套标识，反而更复杂；广播 + 回放已覆盖同一浏览器的所有页面

**前端配套的假死检测**：心跳定时器原本只 `send("ping")` 但从不检查 pong，连接假死时前端会一直以为自己在线。改为记录「最近一次收到任何服务端消息的时刻」，超过 70s 完全静默就主动 `close()` 触发重连，重连后由后端回放补齐。

**另一个连带修复**：`App.tsx` 里把事件挂到「最后一轮对话」时，若本地 `turns` 为空（刷新页面、跨标签页收到事件）会直接 return，导致事件收到了却不显示。现在会按事件补建一条轮次，并借助 `session_created` 事件里新增的 `query` 字段还原用户原始提问。

## ADR-005 外部调用容错：失败降级而非向上抛异常

**背景**：线上出现任务中途中断，前端报 `('Connection aborted.', ConnectionResetError(10054, '远程主机强迫关闭了一个现有的连接。', None, 10054, None))`。截图显示中断前已经成功执行过两次网络搜索，第三次才失败——间歇性，不是被稳定阻断。

**定位过程**：

1. 从异常文本形态判断归属：该元组格式是 `requests`/urllib3 的签名，`httpx`（OpenAI 客户端）不会长这样；且项目内 LLM 走 httpx、搜索走 `tavily` 库，而 `tavily/tavily.py` 顶部就是 `import requests`。**结论：断的是 Tavily 搜索链路，不是大模型**
2. 实测网络：`api.tavily.com` DNS 正常、TCP 可连（1~9 秒，偏慢）；用 `requests` 分别走环境代理和绕过代理直连，均 2 秒内返回 200；官方 `TavilyClient` 同样正常。**排除「服务不可用」与「被墙」，确认是间歇性故障**
3. 结合「前两次成功、第三次失败」的现象定位机制：`TavilyClient` 内部持有 `requests.Session`，默认复用 keep-alive 连接池，而 `requests` 默认 `max_retries=0`。池中一条已被代理或服务端关闭的连接被复用时，直接抛 `ConnectionError` 且**不重试**

**决策**：把「一次网络抖动 = 整轮任务作废」改成「分层重试 + 失败降级」：

```text
传输层：requests.Session 挂 Retry
        connect/read/status 各 3 次、backoff 0.8 * 2^(n-1)、status_forcelist 含 429/5xx
        ⚠ allowed_methods 必须显式加 POST —— urllib3 默认只重试幂等方法，搜索是 POST
应用层：传输层重试耗尽后整体再试 2 次（覆盖代理抖动）
失败降级：仍失败 → 不抛异常，返回 JSON 错误说明 + 上报 tool_error 事件
```

**为什么失败要降级成返回值而不是继续抛**：工具异常会顺着 LangGraph 冒到图顶层，触发 `run_deep_agent` 的兜底分支，**把本轮已搜集的资料一并作废**。返回一段结构化错误（含 `reason` / `detail` / `guidance`）则让模型有机会换关键词重搜、改用数据库或知识库助手，或如实说明该部分缺失——这正是 agent 该有的自愈行为，也避免模型在检索失败时凭记忆编造内容。

**配套的三处改动**：

1. `monitor` 新增 `tool_error` 事件，与任务级 `error` 区分：前者表示「这次工具没取到结果，任务仍在继续」，后者表示「整轮中断」。同时新增 `report_error` 公开方法（原先外部直接调用私有的 `_emit`，属于坏味道）
2. `run_deep_agent` 的异常兜底：错误信息带上异常类型与原因；若此前已有产出，用 `report_task_result(partial=True)` 交付**部分结果**，前端标注「已中断」并提示信息不完整，避免用户把半成品当成完整交付
3. 不可重试的错误（密钥无效 / 配额耗尽 / 权限不足 / 参数错误）按类名识别后立即失败，不浪费重试次数和配额

**放弃的方案**：

1. ~~只在 `main_agent` 外层加重试重新执行整轮~~——会重复消耗已有上下文和配额，且 LangGraph 图已按线程打点，重入容易产生重复消息；根因在单次 HTTP 调用，应在最靠近故障处修复
2. ~~给模型再包一层「搜索失败自动换词重试」的包装工具~~——把决策权从模型手里拿走，且换词质量不如模型本身；降级为返回 `guidance` 让模型自己决策
3. ~~换用 tavily 的 `AsyncTavilyClient`（走 httpx）~~——httpx 对连接池失效的处理同样依赖显式重试配置，换库不解决根因，反而引入同步/异步工具混用问题

## ADR-006 知识库信源：用自建 RAG 整体替换 RAGFlow

**背景**：项目一（电商问数）的 Qdrant / Elasticsearch 是 NL2SQL 的 schema 召回，不是文档 RAG；本项目此前接入 RAGFlow 的方式是「向 RAGFlow Chat 助手提问」——提取、切分、embedding、检索、生成全部发生在 RAGFlow 内部，自己的代码里没有一条 RAG 链路。也就是说，文档切分、Embedding、检索与上下文构建这几环，在本仓库中没有代码归属。

**决策**：整体移除 RAGFlow 依赖，自建轻量 RAG 模块（`app/rag/`），架构上做两个关键改变：

1. **检索与生成分离**。原方案把问题转发给 RAGFlow Chat 拿现成答案（R 和 G 都在外部服务里）；新方案工具只返回检索到的**原文片段**（含来源文档与章节），由知识库子智能体亲自阅读、筛选、综合——检索（R）是自建模块，生成（G）是子智能体，这才是标准的 RAG 架构，也把「知识库助手」从传话筒变成了真正的专家。
2. **双路检索 + 优雅降级**。BM25（jieba 分词）始终可用；embedding 端点独立可插拔（`EMBEDDING_*` 三项环境变量），配置齐全时走「BM25 + 向量余弦」双路召回，用 RRF（Reciprocal Rank Fusion）融合排序——两路得分量纲不同（词频统计 vs 余弦），RRF 只看排名不看分值，免调参。embedding 未配置时自动降级纯 BM25，不报错不阻塞。

**端点事实（实测）**：项目当前 LLM 端点仅有两个对话模型（`/v1/models` 实测），无 `/v1/embeddings`（404）。因此 embedding 不能复用 LLM 配置，必须独立接入 OpenAI 兼容的 embedding 服务（硅基流动 / DashScope 等），并通过降级设计保证零额外配置时系统仍可运行。

**切分策略**：结构感知——Markdown 按 `#` 标题、DOCX 按 heading 样式、PDF 按页提取，块内超长再按中文句读下钻，目标 600 字符 + 100 重叠。切分质量是 RAG 检索质量的第一决定因素，按标题/句子边界切出的块才能独立成义。

**摄入与增量**：`python -m app.rag.ingest` 扫描 `docs/knowledge_base/`（目录即知识库），按文件 sha256 增量摄入；原文落盘为 `chunks.jsonl`，chunk 向量写入 Qdrant（见 ADR-007），`meta.json` 记录文件哈希与索引模式。

**放弃的方案**：
1. ~~保留 RAGFlow，只给附件信源加轻量 RAG~~——工程量最小，但知识库主链路仍是调外部服务，两个项目依然没有一条完整自建 RAG 链路（评估后用户拍板整体替换）
2. ~~引入 Qdrant / FAISS 等向量库~~——知识库规模是 5 份 PDF、数百 chunk，numpy 全内存余弦检索毫秒级返回，引入向量库属于堆砌名词，违背「最小够用」原则
   > ⚠️ 此条已被 **ADR-007** 修订：保留「该规模下向量库没有性能收益」的判断，但基于按元数据过滤、持久化服务形态与可观测性的需要，最终引入 Qdrant 作为向量后端。
3. ~~本地跑 embedding 模型（bge-m3）~~——2GB+ 模型下载、CPU 推理秒级延迟，教学项目不值；远程 API 一行配置即用
   > 后续演进：最终采用 **本地 TEI 容器 + bge-large-zh-v1.5**（1.3GB，CPU 可跑、离线、无 key），兼顾了「不依赖外部 API」与「部署简单」。
4. ~~加权拼接两路得分~~——BM25 与余弦分数量纲不可比，融合权重需要评测集校准，RRF 按排名融合天然免调参

**设计要点**：切分为什么按结构不按固定长度；BM25 与向量检索各自覆盖什么 case（精确术语 vs 语义改写）；RRF 为什么免调参；检索生成为什么要分离（可换生成模型、可观测、子智能体可多角度检索）。

## ADR-007 向量存储：引入 Qdrant 作为向量后端

**背景**：ADR-006 决定自建 RAG 后，向量最初以本地 `vectors.npy`（numpy 矩阵）存储，检索时全量载入内存做余弦计算。该方案在 617 个 chunk 的规模下性能完全够用，但暴露三个问题：

1. **无法按元数据过滤**——「多知识库」只能靠一个目录一份索引硬隔离，做不到「在某份文档内检索」或「跨库检索并标注来源」；
2. **存储形态不是服务**——索引与代码同目录，多进程/多实例部署时无法共享，也不符合生产系统的部署形态；
3. **不可观测**——命中了什么、向量怎么分布，没有任何可视化手段，演示与排查都靠打日志。

**决策**：引入 Qdrant 作为向量后端（`app/rag/vector_store.py`），并做如下取舍：

1. **单 collection + payload 过滤**，而非「一个知识库一个 collection」。payload 携带 `kb / seq / chunk_id / doc / heading / text`，检索时用 `kb` 字段过滤。新增知识库无需建新表，并为「跨库检索 + 按来源过滤」留出演进空间。
2. **原文与向量分离存储**：原文仍在本地 `chunks.jsonl`（BM25 路的数据源），向量在 Qdrant，两者通过 chunk 在 jsonl 中的行号（`seq`）对齐，RRF 融合在应用层完成——BM25 路因此不依赖向量库。
3. **point id 用 `uuid5(kb::chunk_id)` 派生**，确定性 ID 让重复摄入天然幂等（upsert 命中同一点，不会产生重复）。
4. **不可用时降级而非报错**：`QdrantVectorStore` 连接/查询失败抛 `QdrantUnavailable`，检索层捕获后退回纯 BM25 并只告警一次。向量库是检索质量的增强项，不是系统可用性的前提。
5. **改用 Qdrant 后移除 `vectors.npy`**，避免两套向量存储并存导致状态不一致。

**为什么不选 Chroma**：Chroma 定位是嵌入式优先（默认直接写本地 SQLite + parquet），docker 化的意义有限；并发与生产部署能力较弱（官方定位为轻量单机方案）；Windows 上依赖较重。本项目需要的是「docker 内独立服务 + 生产部署形态」，Qdrant 更匹配。

**与项目一的区别**：项目一（电商问数）用 Qdrant 做 NL2SQL 的 schema 召回（按表名/字段做 payload 过滤，服务于 schema linking）；本项目用 Qdrant 做文档 chunk 检索（按知识库/文档过滤）。同一工具、不同场景与建模方式。

**规模诚实说明**：617 个 chunk 的规模下，向量库相对 numpy 全内存检索没有性能收益（numpy 精确检索微秒级，ANN 近似反而更慢）。引入的正当理由是**按元数据过滤、持久化服务形态、可观测性**，而非性能。若规模继续增长，Qdrant 的 HNSW 参数（`m` / `ef_construct` / `hnsw_ef`）才成为真正的调优对象。

**放弃的方案**：
1. ~~继续用 `vectors.npy` + numpy 全量检索~~——性能够用，但无法过滤、不可观测、非服务形态
2. ~~用 Chroma~~——嵌入式优先，与「docker 内独立服务」的诉求错位
3. ~~一个知识库一个 collection~~——新增知识库要建表，且无法做跨库检索
4. ~~在应用层手写 HTTP 调用 Qdrant~~——官方 `qdrant-client` 已覆盖序列化、过滤构造与超时，自己写只会更脆

**设计要点**：这个规模为什么还上向量库（诚实回答：为过滤能力与部署形态，不为性能）；单 collection + payload 过滤 vs 多 collection 的取舍；向量库不可用时如何降级（embedding → Qdrant → BM25 三级链路）；point id 为什么用确定性 UUID。

## ADR-008 关键词检索：引入 Elasticsearch 作为关键词路后端

**背景**：ADR-006 自建 RAG 时，双路检索的「关键词路」用的是进程内 `rank_bm25`（jieba 分词 + Okapi BM25）。它与向量路存在不对称：

1. **没有倒排索引**——每次查询对全量 chunk 打分排序。617 条时是微秒级，但这是**结构性问题**：语料一涨就是线性劣化，而倒排索引是这个问题的标准解；
2. **分词不可配**——jieba 只有一个通用词典，无法做到「索引期细粒度切分提召回、查询期粗粒度切分提精度」这种搜索工程里的常规手段，也没有领域词/停用词的可运营入口；
3. **不是服务形态、不可观测**——与 ADR-007 给向量路列出的理由同构：无独立进程、无法多实例共享、没有 dashboard，也没有 `_analyze` / `explain` 这类相关性调试工具。

**决策**：引入 Elasticsearch 8.19 作为关键词路后端（`app/rag/keyword_store.py`），进程内 `rank_bm25` 降级为兜底实现。具体取舍：

1. **单索引 + `kb` 字段过滤**，与 Qdrant 的建模方式对称（Qdrant 单 collection + payload 过滤）。检索用 `bool.must(multi_match) + filter(term: kb)`——`filter` 不参与打分，等价于 Qdrant 的 payload filter。正文权重 1.0、章节标题权重 2.0（标题命中通常意味着整段相关）。
2. **`_id` 用 `uuid5(kb::chunk_id)` 派生**，与 Qdrant 的 point id 同一套确定性规则，重复摄入天然幂等（`_id` 相同即覆盖）。
3. **自建镜像装 IK 分词插件**（`docker/elasticsearch/Dockerfile`）。ES 内置 `standard` 对中文按单字切分，检索精度差；`analysis-ik` 提供 `ik_max_word`（索引期，细粒度）与 `ik_smart`（查询期，粗粒度），是中文场景的事实标准。插件包随仓库提供（4.5MB），构建不依赖外网——**clone 后 `docker compose build` 一定能成功**。
4. **分词器探测可回退**：启动时用 `_analyze` 探测 `ik_max_word` 是否可用，缺失则退回 `standard` 并告警。装了 IK 效果最好，但插件缺失也不能让系统崩。
5. **不可用时降级而非报错**：连接/查询失败抛 `ElasticsearchUnavailable`，检索层捕获后回退进程内 `rank_bm25` 并只告警一次。关键词路是知识库检索的基本盘，ES 只是它的**加速与提精实现**。
6. **部署参数按本机资源定**：`ES_JAVA_OPTS=-Xms512m -Xmx512m`（本机总内存 8GB，且要同时跑 1.3G 的 embedding 模型与 Qdrant；617 chunk 的索引极小，512MB 绰绰有余——不限制的话 ES 会按宿主内存取一半即 2GB+）；`xpack.security.enabled=false` 本地开发省去证书配置；对外端口 9201 避开本机可能已被占用的 9200。

**为什么不干脆让 ES 一个系统同时承载向量与关键词**（这是一个常见的追问点，ES 8.0 起 `dense_vector` 已支持 HNSW kNN）：

1. **Qdrant 在纯向量检索上更专精**：量化压缩、过滤与向量检索的联合优化、多向量（ColBERT 式）等能力是它的主业；ES 的 kNN 是「够用」级而非专精级。1024 维 float32 向量放进 ES 还会显著放大索引体积。
2. **架构显性化本身就是目的**：本项目的关键设计之一是「双路检索 + 应用层 RRF 融合 + 分级降级」。全部塞进 ES 后，检索退化成一个不透明的黑盒调用——RRF 融合、单路对比实验、降级链全部消失，等于把最有讲头的部分藏起来。
3. 真实系统里「专用向量库 + 专用搜索引擎」的分工也是常见形态。

**为什么不直接删掉进程内 `rank_bm25`**：它承担两件事——ES 不可达时的降级路径，以及**零依赖离线演示**（不启任何容器也能检索知识库）。代价是维护两条代码路径，因此它被限制为「仅在 ES 缺席时执行」，且评测集可以量化两者的效果差（`python -m app.eval.eval_retrieval --mode bm25` 与 `--mode keyword` 两组的对照）。

**诚实说明**：617 个 chunk 的规模下，进程内 `rank_bm25` 的性能不是瓶颈（微秒级全量打分）。引入 ES 的正当理由与引入 Qdrant 同源——**倒排索引解决的是规模曲线问题、IK 分词解决的是中文检索精度问题、服务形态与 dashboard 解决的是可观测问题**，而不是「现在跑不动」。

**放弃的方案**：
1. ~~关键词路只用进程内 `rank_bm25`~~——无倒排索引（结构性瓶颈）、分词不可运营、不可观测
2. ~~让 ES 的 `dense_vector` 同时承载向量与关键词，去掉 Qdrant~~——见上，专业化程度与架构显性化双重考虑
3. ~~装 ES 但不装 IK，用内置 `standard`~~——中文按单字切分，`股票市场` 会被拆成 4 个单字，召回噪音大
4. ~~写一个 jieba 的 ES 自定义分词插件~~——工程量与长期维护成本远超收益，IK 已是成熟方案
5. ~~用 Elasticsearch 替换 MySQL 做结构化查询~~——两者职责不同，业务数据仍走 MySQL（见「框架选型」）

**设计要点**：BM25 是算法、ES 是引擎（ES 7.0 起默认打分器即 BM25，底层 Lucene）——本项目关键词路用的是 ES 的 BM25，降级路径用的是 `rank-bm25` 库，两者是同一算法的不同实现；`ik_max_word` 与 `ik_smart` 为什么分索引期与查询期两个粒度；`must` 与 `filter` 的区别（后者不参与打分、可缓存）；为什么双路检索而不是单路（关键词负责精确术语与专有名词，向量负责语义改写与同义表达）；三级降级链在什么情况下各触发哪一级。

## ADR-009 评测指标对齐 RAGAs 体系：只补 Answer Relevancy，不引入 RAGAs 框架

**背景**：阶段四评测需要一套完整、能与业界对标的指标体系。通用 RAG 评测（RAGAs 框架）把评估分两层——检索层（Hit@K、MRR）与生成层（Faithfulness、Answer Relevancy、Context Recall、Context Precision）。逐条比对后确认：本项目已有的指标已覆盖其中 5/6，仅 **Answer Relevancy（答案相关性 / 切题度）** 无对应物。

**现状映射**（为什么只缺口一个）：

| 业界指标 | 本项目对应物 | 说明 |
|---|---|---|
| Hit@K（检索层） | `正确文档率` + `全命中题率@5` | 文档级命中，已有 |
| MRR（检索层） | `MRR` | `app/eval/eval_retrieval.py`，口径完全一致 |
| Faithfulness | `幻觉率`（judge 的 `unsupported_claims`） | 同义反向，已有 |
| Context Recall | `Recall@k`（事实锚点版） | **比 RAGAs 的 LLM 打分更客观**——锚点可复现、可争论，不掺主观 |
| Context Precision | `MRR` + `正确文档率` 近似覆盖 | 均为「相关内容排名是否靠前」 |
| **Answer Relevancy** | **无** | 唯一缺口：现有 `completeness` 只测答得全不全，测不出跑题 |

> **2026-10-10 更新**：上表中检索层两行的对应物已随指标重定而变化——现在有了显式的
> `Context Precision@5`（chunk 级 AP@5）与统一命名的 `Context Recall@5` / `MRR@5`，
> 见 **ADR-011**。本表保留为 ADR-009 决策当时的现状快照。

**决策**：在 LLM-as-judge 层**新增 `answer_relevancy`（1–5）字段**及其派生指标「答案相关性」，补齐唯一缺口；**不引入 RAGAs 框架本体**。

**理由**：
1. **范式不匹配**——RAGAs 面向「单轮 RAG 问答」（question → retrieve → answer），本项目是 deep research agent（规划 → 多轮检索 → 反思 → 综合）。RAGAs 的 Context Recall 强依赖 ground truth，套在多轮研究任务上水土不服，而 `eval.md` 已明确「输出是研究报告，不是短答案」。
2. **技术摩擦**——RAGAs 重度依赖结构化输出，而本项目 LLM 端点**不支持 `json_schema`、只能用 `json_mode`**（ADR-002），集成需打补丁。
3. **自建 eval 是资产**——`app/eval/`（事实锚点 + 三层判分 + 落盘不覆盖）是自建能力，比「调了 RAGAs」更能体现工程判断力。
4. **补的是真空白**——`completeness` 与 `answer_relevancy` 正交：「答得全不全」与「答得切不切题」是两回事，前者测不出「有据但跑题」。

**放弃的方案**：
1. ~~引入 RAGAs 框架做生成层评测~~——范式错配 + `json_schema` 不可用 + 稀释自建 eval 的叙事价值
2. ~~用 RAGAs 的 LLM 打分替换现有事实锚点法~~——锚点法更客观，属能力倒退
3. ~~同时补 Context Precision 显式指标~~——`MRR` 已近似覆盖，边际收益低（保留为可选 TODO，见下）
4. ~~什么都不加~~——`Answer Relevancy` 缺口会在「agent 引对 chunk 但答偏问题」时完全不可见

**待校准事项（不是决策，是执行前提）**：业界经验阈值（如 Hit@5 < 0.7 换模型、MRR < 0.5 说明 Rerank 不足、Answer Relevancy > 0.8 达标）**不可直接照抄**——本项目无独立 Rerank 层、评测样本仅 5~6 题/单文档 6 题。任何验收阈值必须先用全量重建后的真实基线跑出来再写进 `eval.md`。

**设计要点**：为什么 `answer_relevancy` 要用 LLM 判而 `Context Recall` 坚持用事实锚点（前者是主观语义判断、无客观锚点；后者有原文可查，能程序化）；judge 输入为何不含执行轨迹（避免被过程带偏，只评结果）。

## ADR-010 跨语言检索：字段级语言路由（关键词路的 zh_text 视图）

**背景**：全量评测（39 条查询 / 13 题 / 36 个锚点，见 `app/eval/` 与 `.workbuddy/scripts/bench_schemes.py`）暴露一个反直觉现象：**双路融合比向量单路更差**——整体 Recall@5 原始 RRF 54.9% < Vector only 58.3%，中文 Query 组尤其悬殊（46.2% vs 69.2%），同一份 ICCT 英文报告上中文问句的 `Recall@5` 一度为 **0%**。

只读诊断（`.workbuddy/scripts/diag_rrf_pollution.py`）定位到根因，**不是**「几个噪声块」，而是 RRF 的结构性奖励：

1. `_rrf_fuse` 的 `score = Σ 1/(60+rank)` **只用名次、丢弃原始分值**（ES `_score` 最高 10.32 与 3.88 在融合眼里同量级）。于是**「两路都命中」的块必然赢过「单路排第 1」的块**——实测中文 query 下，向量路排第 1、唯一命中锚点的块 RRF 分与纯噪声块相同（0.0164），被挤到第 6。
2. 中文 query 经 IK 切出的拉丁 token（`BEV` / `LDV` / 数字）与英文原文形成**假公共 token**，让 ES 返回一批「含该字样但非答案」的块（页眉、泛述段），这些块在向量路也语义沾边 → **双路命中 → 双路加分**。
3. **关键判断**：问题不是「有几个坏块」，而是**「一条在特定语料上系统性失效的路，在等权 RRF 里仍拿到与有效路同等的候选席位」**。反事实实验证实这个判断——只剔除明显的中文碎片块（`cjk≥0.30`），`Recall@5` 纹丝不动（0%）；放宽到剔除全部含中文的块（`cjk≥0.02`）也只恢复到 **15%**，而向量单路 Top-20 本来就有 **70%**。

**决策**：给关键词路做**字段级语言路由**——正文拆成两个可检索字段，由查询语言选择打哪个，而不是在结果集上做过滤。

1. **摄入期**（`app/rag/language.py` + `chunker.py` + `ingest.py`）：每份文档合并全文后做一次**文档级**语言判定，给该文档所有 chunk 盖上 `lang`（zh/en）、`cjk_ratio` 两个字段，并由 lang 派生 `zh_text`——**中文文档 = 原文，英文文档 = 空串**。
2. **检索期**（`keyword_store.search(..., query_lang=...)`）：中文 query 只打 `zh_text`，中英混排 query 两个正文字段都打。英文文档的 `zh_text` 为空 → 中文 query 在英文文档上**命中天然为空**，关键词路在跨语言场景下**整体退出**、融合自动退化为向量单路。（原「英文 query 只打 `text` + `heading`」一条已随英文查询支持下线，见本节末尾修订。）
3. **库级短路**（`retriever._keyword_route_applicable`）：库内语言集合与查询语言完全不重叠时（如中文 query × 纯英文库）**整路跳过**，省掉一次 ES 查询，且比「查完再过滤」更干净。
4. **必须文档级判定，不能块级判定**：英文报告里的中文碎片块实测 `cjk≈0.15~0.17`，按块判定会被判成「中文块」——而它们恰恰是噪声源。文档级判定（整份合并后 ≥0.20 视为中文）把它们正确归到英文文档下，`zh_text` 为空，从根上出局。

**效果（四方案全指标实测，13 题 × 3 语言 = 39 条查询）**：

| 方案 | Recall@5 | Recall@20 | MRR@5 | NDCG@5 |
|---|---|---|---|---|
| Vector only | 58.3% | 90.6% | 0.516 | 0.424 |
| 原始 RRF（等权） | 54.9% | 88.0% | 0.471 | 0.383 |
| **语言门控 / 字段路由** | **64.1%** | **90.6%** | **0.549** | **0.441** |
| 加权 RRF（w_kw=0.3） | 56.6% | 90.6% | 0.472 | 0.400 |

语言门控是**唯一 Pareto 最优**方案——三种查询语言 × 五个指标上「不低于任何其他方案」。机制上它同时兑现了两件事：中文 query 在纯英文库上 keyword 候选**全空（7/7）** → 退化为向量（找回被 RRF 拖掉的基线）；中文 query 在中文库上 keyword **照常生效（0/6 为空）** → 同语言增益一个没丢。

**为什么用「字段路由」而不是「结果级过滤」**：过滤是**事后**的——噪声块已经进了候选、已经参与打分，只能靠阈值事后剔除；实测剔除后最多恢复到 15%，而正确答案本身也是「含中文的块」时会连答案一起剔（`cjk≥0.30` 的口径下那些碎片块反而够不到阈值，`Recall@5` 依旧是 0%）。字段路由是**事前**的——噪声块根本不在被检索的字段里，不需要任何过滤条件，也不存在「阈值取多少」的调参问题。

**为什么 `zh_text` 对英文文档留空（最小版）而不是填译文**：填译文能让中文 query 在英文文档上也走关键词路，但它需要把整库英文文档翻译一遍——引入 LLM 批量调用、成本与不确定性，且收益未经测量。留空版本**零成本、零新增依赖**，效果已被实测锁定为与语言门控等价（整体 Recall@5 64.1%）。译文是**可选的第二段实验**（"用翻译桥接跨语言关键词匹配"），不是这个决策的前置条件。

**为什么向量路不做语言过滤**：跨语言时向量是英文文档**唯一**的召回手段（实测 vector 单路 Top-20 已有 70%），给它加语言门控等于自断退路。语言字段仍写入 Qdrant payload，但只用于 dashboard 可观测，不参与过滤——`lang` / `cjk_ratio` 落库，`zh_text` 不入 Qdrant（它是 ES 专属视图，存进向量库纯属冗余）。

**为什么不干脆给 RRF 加权、或改成用分数融合**：加权 RRF 是最弱的杠杆——`w_kw` 从 0 扫到 1.0，整体 Recall@5 只在 55~58% 间波动、无单调改善（0.3 时仅 56.6%），远不如门控的 64.1%。**根因在于加权仍让失效路保留席位，只是把它的权重调小**；而失效路的噪声恰好与有效路的噪声重叠，权重调小压不住「双路命中」的结构性奖励。分数融合则要面对 BM25 分值与余弦相似度量纲不可比的老问题（正是 RRF 被引入的原因，见 ADR-008）。

**放弃的方案**：
1. ~~结果级过滤（按块语言剔候选）~~——事后过滤，实测最多恢复到 15%，且与答案同语言特征时会把答案一起剔掉
2. ~~加权 RRF~~——w_kw 扫描无单调改善，验证为弱杠杆
3. ~~一刀切砍掉关键词路（w_kw=0）~~——混合 Query 组恰恰需要它（69.9% vs 纯向量 55.1%），砍掉等于用 A 组的收益换 C 组的损失
4. ~~用 LLM 判定语言~~——摄入链路不允许引入外部调用；`cjk_ratio` 纯本地、零成本、可复现，且覆盖不了的情况（真正的短句中英混排）恰好该归到 mixed 而不是任何一侧
5. ~~英文文档的 `zh_text` 填机器译文~~——成本与不确定性高、收益未测，保留为后续独立实验（见上）
6. ~~换掉 embedding 模型~~——kb-10 的 0/6 已被证实是**跨语言排序问题而非模型能力问题**（英文问句能把锚点排到第 1、同题中文问句 @80 能到 95%），换模型不解决「失效路占等权席位」这个结构问题。换 Qwen3-Embedding-0.6B 另立为独立对比实验

**诚实的边界说明**：语言路由解决的是「失效路拖累融合」，**不是**「跨语言检索本身」。中文 query 打英文文档仍然只能靠向量弱对齐（天花板约 @40=80%，低于英文的 @20=95%）。要真正跨过这道坎，需要的是 rerank 精排（把已召回的锚点从 40 名内提到前面）与 query 改写，不是本条决策的目标。

**待校准事项**：`LANG_DOC_ZH_MIN_RATIO=0.20` / `LANG_QUERY_ZH_MIN_RATIO=0.30` **均为先验值，未做校准实验**（当前语料规模不足以扫描）。阈值只负责**路由决策**，不负责隔离——真正的隔离由 `zh_text` 字段完成，所以这不是关键参数：即使阈值取错，最坏结果也只是把一条 query 分到 mixed（两个字段都打），不会让噪声块混进来。

**设计要点**：为什么 `cjk_ratio` 的分母用「非空白字符数」（英文的词间空格会稀释比例）；为什么文档级与查询级要用两套阈值（query 短、比例分布不同）；`zh_text` 为什么用与 `text` 完全相同的 IK 分词器（同语言增益不能丢）；库级短路为什么等价于字段路由而不是额外优化（候选必为空的查询，跳过与查完得到空集在结果上等价，只省延迟）；`meta.schema` 版本号为什么必须存在（新增字段时文件哈希不变，仅凭哈希会把「字段没补上」误判成「无变化」，索引会永远补不齐）。

**修订（2026-10-12 晚）：下线纯英文查询。** 项目定位为**中文提问**的检索系统，故把「英→中 / 英→英」两条链路整体移除，只保留中文（zh）与中英混排（mixed）两类查询。改动面：

- **题库**：`retrieval-tasks.yaml` 删除 30 题的 `en` 问句（保留 `zh` 与 `mixed`），共 33 题 / 63 查询。
- **检索期代码**：`classify_query` 删除「≤0.02 判 en」分支（只返回 `zh` / `mixed`）；`keyword_store._SEARCH_FIELDS_BY_LANG` 移除 en 字段组；`config.LANG_QUERY_EN_MAX_RATIO` 常量删除。
- **评测脚本**：`eval_retrieval.py` 的 `--lang` 白名单开关、`QUERY_LANGS` 机制删除（口径固定为 `LANGS_ALL = ("zh", "mixed")`）。

**未被破坏的部分**：文档级语言判定（`classify_document`）、`text` / `zh_text` 双字段、`zh_text` 中文视图——它们是「中→英」（中文问句检索英文文档）的基础，**照常保留**。故本 ADR 的核心机制（字段级路由）不变，只是不再有「英文查询」这一输入端。mixed 查询仍打 `text` + `zh_text` 两个字段（英文文档的 `zh_text` 为空，必须靠 `text` 命中）。

## ADR-011 评测指标重定：检索层对齐业界六指标口径

**背景**：检索层原有指标集（Recall@1 / @3 / @5、Hit@1、MRR、全命中题率@5、正确文档率）是为「定位单文档 / 单库检索故障」逐步长出来的——它确实帮我们发现并修掉了切分退化、RRF 双路奖励、跨语言失配三个真问题，但作为**对外口径**存在明显缺陷：

1. **命名不与业界通用**——`Recall@k` / `全命中题率` 对不上 RAGAs 的 Context Recall / Context Precision，简历与面试里要额外解释，且无法与他人结果对照；
2. **列多而目标不清**——`Recall@1` 测的其实是「单块信息密度」（单块仅 ~400 字，一题多事实天然分散），却被当成检索质量读；已因此误判过一次（用户问「Recall@1 是不是太严格」）；
3. **缺位置加权的精度指标**——`MRR` 只看「第一个」相关结果，回答不了「Top-5 里相关块的**占比与排布**是否合理」；
4. **完全没有性能指标**——检索是 agent 的同步阻塞环节，延迟直接决定体验，此前只随手记均值。

**决策**：检索层指标重定为六项，与业界 RAG 评测体系对齐（用户 2026-10-10 给出清单）：

| 类型 | 指标 | 口径 | 落地 |
|---|---|---|---|
| 检索质量 | **Context Recall@5** | fact 级 micro：Top-5 覆盖锚点事实数 / 锚点总数 | `app/eval/eval_retrieval.py` |
| 检索质量 | **Context Precision@5** | chunk 级 **AP@5（位置加权）**，相关块 = 含任一锚点 | 同上 |
| 检索质量 | **MRR@5** | chunk 级：首个相关块排名倒数，Top-5 外记 0 | 同上 |
| 答案质量 | **Faithfulness** | LLM judge 逐论断判「有无 chunk 支撑」 | **第二阶段** |
| 答案质量 | **Answer Correctness** | LLM judge 与**参考答案**比对 | **第二阶段** |
| 性能 | **P95 延迟** | 逐条 wall-clock 的 95 分位（附 P50 / max） | `app/eval/eval_retrieval.py` |
| 检索质量 | **NDCG@5**（追加） | chunk 级二值：DCG = Σ relᵢ/log₂(i+1)，NDCG = DCG/IDCG | 同上 |
| 检索上限 | **候选池召回**（追加） | 融合去重后、截断成 top-5 之前的候选集合覆盖的锚点比例 | 同上 |

配套的结构调整：**题库外置**为 `app/eval/retrieval-tasks.yaml`（13 道双语题 × 3 语言 + 5 道单语题，含锚点校准铁律），评测脚本不再内嵌题目；删除已被取代的 `eval_retrieval.py`（旧版）/ `compare_retrieval.py` / `.workbuddy/scripts/test_single_doc.py` / `test_icct_bilingual.py`；保留 `eval-tasks.yaml`（端到端评测集）、`reporting.py`（落盘不覆盖机制）与 `results/`（历史基线，用于改口径前后的对照）。

**为什么 Context Precision 用 AP@5 而不是裸占比**：用户的诉求是「排序**与占比**是否合理」，而裸占比（相关块数 / 5）位置无关——第 1、3 位相关与第 4、5 位相关得分相同，答不出「排得靠后」这个我们真正的病灶（ICCT 英文题 @5=45% 而 @20=95%，全是排序问题）。AP@5 = Σ_{i: 相关} (前 i 个中相关数 / i) / R 同时含占比与位置：同样 2 个相关块，排第 1、3 位得 0.83，排第 4、5 位只有 0.35。报告里**同时保留裸占比作参考列**，两者对照即可区分「相关块太少」与「相关块排得太后」。

**为什么相关块用锚点近似判定**（含任一锚点即相关），而不做逐题 gold chunk 标注：零标注成本、与 Context Recall 同源、可交叉解释。**代价必须诚实说明**：语义相关但不含锚点的块会被判为不相关，AP@5 绝对值偏低——它适合做**同一套题内的方案对比**（跨方案结论不受影响），不适合当作与别人家 RAGAs 数值的绝对对标。若将来确需与 RAGAs 数值直接对齐，再补逐题 gold chunk 集。

**为什么 Context Recall 坚持锚点法而非 RAGAs 的 reference-based 口径**：RAGAs 需要参考答案、再逐句判「能否归因到某 chunk」，是 LLM 判分，噪声大且不可复现；锚点法把同一语义变成「可从原文客观判定的字符串（数值、专名、术语）」，每个数字可争论、可复现。代价是**只覆盖可客观判定的那部分事实**（描述型事实不入库），这既是它的边界也是它的硬度来源。

**为什么生成层两个指标分到第二阶段**：Faithfulness 需要真实生成的答案，Answer Correctness 还需要**参考答案**这一全新标注资产，两者都依赖 LLM judge 的落地（协议见 `eval.md` 3.2，代码未实现）。顺序是先把检索层口径稳定下来（含随后的 rerank），再做生成层。届时还需决定评测对象：评「给定检索结果 → 单轮 RAG 回答」（可控、能隔离检索质量与编排质量）还是「agent 最终研究报告」（贴产品形态、需跑完整 agent、参考答案要到报告粒度）。

**P95 的两个口径边界（写进报告，避免误读）**：① 题库 39 条查询时 P95 ≈ 第 2 慢那条，统计上不稳健，故报告同时给 P50 / max 与样本数，不单看 P95；要真正谈 P95 需 ≥100 条查询。② 这是**检索延迟**（两路检索 + RRF + query embedding，百毫秒级）；**端到端延迟**（含 LLM 生成，秒到分钟级）属生成层，两者不混表。

**保留的诊断列**：`--diag` 附带 `Context Recall@20`。它不在用户要求的六项里，但**是区分「没召回」与「排得靠后」的唯一工具**（ADR-010 的整个诊断就靠它），默认不跑来控制成本。

**口径扩展（2026-10-10 追加，同属本决策）**：在六项之外增补两项，服务「rerank 之前先把尺子补准」这个目标（用户 2026-10-10 的对照实验口径里指定了 NDCG@5）：

- **NDCG@5**（标准归一化折损累计增益，二值相关性）：DCG = Σ relᵢ/log₂(i+1)，IDCG = 相关块全排最前时的 DCG，NDCG = DCG/IDCG。与 AP@5 同为「位置敏感 + 归一化」，但对「排太后」惩罚更平缓（对数折扣 vs 逐点精度平均）——两者并排能分出「相关块太少」与「相关块排太后」。
- **候选池召回（检索上限）**：融合去重后、**截断成 top-5 之前**的候选集合覆盖的锚点比例。rerank 只能在此集合内重排，故它就是本配置下 Recall@5 的**理论上限**；「候选池召回 − Recall@5」= 精排可吃掉的排序空间。它随 `--diag` 追加**池召回@100/路**（每路候选从 15 加深到 100），用来固化「加深池即可覆盖几乎全部锚点」。

实现上给 `Retriever` 增了两个**只读**方法（`search_with_pool` / `candidate_pool`），`search` 的行为一字未改——候选池与 Recall@5 共用同一次检索的产物，池召回**零额外成本**。

**为什么要单列「候选池召回」——2026-10-10 修正的一次方法论错误**：诊断初期曾由 `Recall@20 = 88.9%` 反推「12 个锚点没进候选池 = 真召回失败」。这是错的——`Recall@20` 这一路用 `top_k=20 → 每路候选 60`，其候选池比生产（`top_k=5 → 每路 15`）深得多，两者不是一回事。把候选池真正摊开（`.workbuddy/scripts/diag_candidate_pool.py`，depth 100/路）后结论完全反转：**108 个锚点全部在池内（覆盖 100%），池外/较难 = 0**，缺口 100% 是排序问题（见下表）。**教训：不能用 `Recall@K` 的截断输出反推候选池内容，必须把池摊开看。**

**新基线（2026-10-10 18:12，39 查询 / 13 题，ICCT + 贝莱德）**：

| 模式 | ★Recall@5 | ★AP@5 | ★MRR@5 | NDCG@5 | 池召回(生产) | 池召回@100 | 精排可吃 | P50/P95 |
|---|---|---|---|---|---|---|---|---|
| bm25 | 38.0% | 0.326 | 0.342 | 0.359 | 53.7% | 86.1% | +15.7% | 1/3ms |
| keyword(ES) | 35.2% | 0.321 | 0.332 | 0.349 | 51.9% | 66.7% | +16.7% | 55/66ms |
| vector | 54.6% | 0.502 | 0.516 | 0.557 | 79.6% | 100.0% | +25.0% | 165/235ms |
| **hybrid** | **59.3%** | **0.527** | **0.557** | **0.590** | **85.2%** | **100.0%** | **+25.9%** | 214/263ms |

报告落盘 `app/eval/results/2026-10-10_18.12.29__retrieval__bm25+keyword+vector+hybrid.md`。**核心结论**：hybrid 的候选池 @100/路 覆盖 **100%**，「精排可吃 +25.9pt、加深池再 +14.8pt」两块加起来正好补齐全部缺口——**rerank + 适度加深候选池即可吃掉全部，无需改召回手段/换 embedding**。

**放弃的方案**：
1. ~~引入 RAGAs 框架本体~~——理由同 ADR-009（范式错配 + `json_schema` 不可用 + 稀释自建 eval 的资产价值）
2. ~~严格标注 gold chunk 集来算 Context Precision~~——13 题 × 2 库逐块人工标注成本高，锚点近似已足以支撑方案对比
3. ~~这一轮就把生成层两个指标做掉~~——缺参考答案与 judge，强行做会产出不可信数字
4. ~~继续保留 Recall@1 / @3 / Hit@1 / 全命中题率 / 正确文档率~~——目标重复且会误导（@1 已误判过一次）；诊断需要时用 `--diag` 的 @20 更对症
5. ~~只报 P95 一个延迟数~~——小样本下 P95 不稳，必须给 P50 / max / 样本数

**待校准事项（不是决策，是执行前提）**：AP@5 与 P95 都没有「达标线」——业界经验值（如 Hit@5 < 0.7 换模型、MRR < 0.5 说明 rerank 不足）**不可照抄**：本项目无独立 rerank 层、题库仅 39 条查询。任何验收阈值必须先用全量重建后的真实基线跑出来，再写进 `eval.md`。

**设计要点**：AP@5 的算式与「R=0 记 0 而非 1」的理由（没有相关结果时「排得准不准」无从谈起）；为什么 micro 与 macro 两个 Recall 口径要并列报（差距大 = 总分被锚点多的大题主导）；为什么题库要外置成 YAML（加题不改代码、且第二阶段能复用同一批题）；`--list` 为什么要显示各库入库状态（未入库的题必须跳过而不是记 0 分，否则基线被虚低）。

## ADR-012 精排接入生产：进程内 ONNX（CUDA 优先、CPU 兜底），不经过 TEI

**背景**：ADR-011 把检索缺口量化清楚了——hybrid 的候选池（depth 15，池约 21 条）覆盖 **85.2%** 的锚点，而 RRF 的输出 Recall@5 只有 **59.3%**，也就是约 **26 个百分点的锚点已经在池子里却没被排上来**。而且池@100/路覆盖 100%、池外 = 0，说明缺口**100% 是排序问题**，不是召回问题。根因在 RRF 本身：它只看名次不看分值，双路都命中的块必赢单路 rank-1；跨语言时 IK 切出的拉丁 token 与英文原文还会形成「假公共 token」，把噪声块顶上去。这些都只能靠换排序手段解决。

**决策**：引入 cross-encoder 精排作为检索链路的**默认最后一环**（`app/rag/reranker.py` + `Retriever` 的 `hybrid_rerank` 模式），推理走**进程内 ONNX**：

1. **模型**：`bge-reranker-v2-m3`（XLM-R large，568M，fp32 2.2GB）。ONNX 由 `optimum-cli export onnx --task text-classification` 从 `model.safetensors` 导出（`onnx/model.onnx` 图 489KB + `model.onnx_data` 2.27GB 外部数据），**数值与原始权重一致**（logits 最大绝对差 0.0033）。
2. **执行提供器**：CUDA 优先、CPU 兜底。分词用 `tokenizers` 直读 `tokenizer.json`——与 `transformers.AutoTokenizer` 的编码**逐位一致**（前提是 pad id 取 `<pad>`），但导入 0.03s vs 14.8s，不值得为一行便利拖 transformer + torch 进来。
3. **只重排、不增删**：候选集成员不变，所以「候选池召回」仍是 Recall@5 的理论上限，**评测口径无需改动**。
4. **生产默认**：`Retriever.PRODUCTION_MODE = "hybrid_rerank"`，工具层（`search_knowledge_base`）无需感知精排是否存在。
5. **降级而非失败**：模型缺失、依赖未装、CUDA 不可用、推理抛错，`rerank()` 一律返回 `None`，`Retriever` 保持 RRF 原序并只告警一次——检索的可用性不依赖精排。

**效果（2026-10-10 23:13 端到端实测，39 查询 / 13 题 / 36 锚点，ICCT + 贝莱德）**：

| 指标 | hybrid（RRF） | **hybrid_rerank** | 变化 |
|---|---|---|---|
| ★ Context Recall@5 | 59.3% | **84.3%** | **+25.0pt** |
| ★ Context Precision@5 (AP@5) | 0.528 | **0.759** | +0.231 |
| ★ MRR@5 | 0.559 | **0.812** | +0.253 |
| NDCG@5 | 0.591 | **0.815** | +0.224 |
| 命中率@5（占比） | 28.7% | 42.1% | +13.3pt |
| 延迟 P50 / P95 | 215 / 284 ms | **466 / 721 ms** | +251 / +437 ms |

**跨语言组提升最大**——中文Q×英文库 40.0%→70.0%、英文Q×中文库 56.2%→93.8%、混合Q×英文库 55.0%→80.0%，正是 RRF 的「假公共 token」污染被精排修掉的地方。精排后「精排可吃」只剩 **+0.9pt**，**候选池上限基本吃满**（84.3% / 池 85.2%）。

报告：`app/eval/results/2026-10-10_23.13.29__retrieval__bm25+keyword+vector+hybrid+hybrid_rerank.md`

**为什么不走 TEI 容器**（阶段 0 的形态）：TEI 那条路有两个**与模型无关**的遗留问题，进程内调用让它们连同代码路径一起消失：

1. **`queue_time` 排队**：4 条批请求要在服务端队列里干等约 1s（单条请求只等 ~1ms），把 batch 并行的收益（模型前向实测并行 2.13×）整个吃掉，端到端零收益（batch=1 vs 4：870 vs 863ms，1.01×）。注意 TEI 队列**没有时间窗口**——batcher 是 `pop_front` 贪心取尽，所以「等凑批」的说法是错的，它是真的在队列里等。
2. **`core/src/queue.rs:87` 的并发 permit off-by-one**：持续压测下每约 10 个请求 SIGSEGV（Exit 139）一次，且**崩溃会拖垮 Docker Desktop 的 WSL2 VM**，每次在 `%LOCALAPPDATA%\Temp\wsl-crashes\` 落一份 ~3GB 内存转储（实测 3 次 = 9.53GB，把 C 盘吃到只剩 2.8G）。上游 issue #744(CUDA) / #768(M2) 复现同一行 panic——**与后端无关**，换 GPU 也修不掉。

**Windows 上跑 ORT + CUDA 的三个坑**（都踩过，已写进 `_link_cuda_dlls()` 注释）：

1. **`ort.get_available_providers()` 会骗人**——列出 `CUDAExecutionProvider` 只说明 wheel 编译时带了这个 EP；运行期缺 DLL 时 ORT **静默 fallback 到 CPU**（实测跑出过「提速 1.0×」的假结论）。判据必须看 `session.get_providers()[0]`——代码据此在 auto 模式下拦下假 CUDA。
2. **最新 `onnxruntime-gpu 1.31` 要 CUDA 13，而 `nvidia-cublas`(cu13) 在 PyPI 上没有 Windows wheel**（cudnn/cudart/cufft 都有）→ 锁 `onnxruntime-gpu==1.22.0`（CUDA 12 世代）+ `nvidia-{cuda-runtime,cublas,cudnn,cufft}-cu12`（全有 win_amd64 wheel，共 ~1.5GB）。这样不必装 4GB 的 CUDA Toolkit。
3. **`os.add_dll_directory()` 对 ORT 无效**——ORT 以 `LOAD_WITH_ALTERED_SEARCH_PATH` 加载 provider，依赖只在「该 DLL 自身所在目录」解析，用户目录不在搜索范围 → 必须把 DLL **硬链接**到 `onnxruntime/capi/` 同目录（同盘零拷贝；重装 onnxruntime 会冲掉链接，`_link_cuda_dlls()` 每次加载自动补回）。

**三态开关 `RERANK_ENABLED`（默认 auto）为什么这么设计**：`auto` = 仅当 CUDA **真正生效**时启用；`1` = 强制启用（允许 CPU，慢但可用）；`0` = 关闭。auto 之所以卡 CUDA，是为了避免在纯 CPU 机器上把每次检索从 0.2s **静默拖到秒级**——精排在 CPU 上是约 350ms/候选、21 候选就是 7s+。项目 clone 到无 GPU 的机器上时，行为应当是「退回 59.3% 但依然快」，而不是「指标好看但卡死」。

**放弃的方案**：

1. ~~继续用 TEI 容器形态~~——排队与崩溃两个问题都长在 TEI 上，它带来的只是「一个 HTTP 服务」的便利；进程内调用一次省掉容器、HTTP 往返与 Docker GPU 直通三层。
2. ~~精排只跑 top-N（如只重排 RRF 前 8）~~——精排的唯一价值就是把「排名靠后但语义相关」的块提上来，而那恰好是被截掉的那部分；截断等于砍掉精排的价值，不如把池本身缩小。
3. ~~加深候选池到 depth 40/100 去换那 +1.8pt~~——**CPU 上**的代价是 2.75× 延迟（8.8s→24.2s），当时判定不划算。但那是 GPU 之前的结论：GPU 上 4→21 候选单候选仅从 14.9ms 涨到 23.1ms，**池深度的成本结构已经改变**，故保留 `RERANK_CANDIDATE_K` 这个口子待重测，而不是直接否决。
4. ~~换更小的 reranker（`jina-reranker-v2-base` 278M）~~——GPU 上 21 候选整池 460ms、端到端 P50 466ms 已属可交互，无换小模型的必要；保留为纯 CPU 场景的备选。
5. ~~把精排写成 TEI 的可选 `hybrid_rerank` 模式（两套并存）~~——两套推理路径意味着两套部署与两套故障模式，而 TEI 那套已知不稳。

**设计要点**：cross-encoder 与双塔 embedding 的本质差别（前者不能预计算，**每个候选一次完整前向**，成本随池线性；后者文档向量离线算好，线上只编码一次 query）；为什么 `hybrid_rerank` 的融合部分必须与 `hybrid` **完全一致**（这样「精排 vs 不精排」的差异才纯粹来自精排，不受融合行为变化干扰）；为什么 `candidate_pool` 刻意不触发精排（它只回答「候选集里有哪些」，而诊断时会把 `candidate_k` 放大到 100，白跑一次精排没意义）；`RERANK_CANDIDATE_K` 与 `Retriever.candidate_k` 的分工（前者是生产配置、后者是评测传参，传参优先）；「先建 session 再跑一次哑推理」的预热为什么要跑哑推理（CUDA 首次 kernel 编译也在第一次前向里，合计约 3s，必须从首条查询的延迟里摘出去）。

**诚实说明**：84.3% 是在**只有 2 份文档入库**（ICCT 380 chunk + 贝莱德 76 chunk）、13 题 / 36 锚点的小样本上测的，其余 5 题因文档未入库被跳过；延迟 P50 466ms 是**单进程串行**的结果，未测并发下的表现；端到端延迟含检索（~215ms）+ 精排（~250ms），其中精排部分是 GPU 推理，无 GPU 机器会整体降级为纯 hybrid。

## ADR-013 精排候选深度定为 25：深池收益重测（GPU）

**背景**：ADR-012 把精排接入生产时，候选深度沿用 `top_k×3 = 15`（池约 21 条），并在「放弃的方案」里记了一条：CPU/candle 时代测过 depth 40 只换 +1.8pt 却要 2.75× 延迟（8.8s→24.2s），当时判定不划算——但明确留了 `RERANK_CANDIDATE_K` 这个口子「待 GPU 重测」，因为 GPU 上 4→21 候选的单候选耗时只从 14.9ms 涨到 23.1ms，成本结构可能已经改变。本 ADR 就是那次重测的结论。

**重测（2026-10-10 23:20，13 题 / 39 查询 / 108 锚点，ICCT + 贝莱德；报告 `app/eval/results/2026-10-10__rerank-deep-pool.md`）**：

| 每路 K | 池均 | 池召回 | ★Recall@5 | AP@5 | MRR@5 | NDCG@5 | 延迟 P50 |
|---|---|---|---|---|---|---|---|
| 15（原默认） | 21 | 85.2% | 84.3% | 0.759 | 0.812 | 0.815 | 504ms |
| **25（采纳）** | 34 | 91.7% | **87.0%** | 0.761 | 0.808 | 0.821 | 650ms |
| 40 | 52 | 94.4% | 86.1% | 0.758 | 0.806 | 0.819 | 940ms |
| 60 | 73 | 97.2% | 87.0% | 0.764 | 0.813 | 0.830 | 1245ms |
| 100 | 102 | 100.0% | 88.0% | 0.782 | 0.831 | 0.844 | 1668ms |

指标**确定性可复现**：K=25 与 K=100 各复跑一次，Recall / AP / MRR / NDCG 逐位相同，只有延迟 ±2% 波动。

**三条结论**：

1. **候选池上限不是 Recall@5 的瓶颈**。池召回从 85.2% 抬到 100%（+14.8pt 候选空间），Recall@5 只从 84.3% 走到 88.0%（+3.7pt = 4 个锚点）。Top-5 只有 5 个槽位、每题平均 ~2.8 个事实，池再深也塞不进第 6 条。ADR-012 里「精排可吃只剩 +0.9pt」只在 depth 15 的池内成立，不能推论「池没必要加深」。
2. **「GPU 上加候选近乎免费」被证伪**。扣除检索（~0.21s）后折算**单候选 ≈14ms 且几乎恒定**（14.0/13.3/14.0/14.2/14.3）；池 21→102（4.9×）对应精排 0.29s→1.46s（5.0×）——**完全线性**。GPU 只是把单次前向从 356ms 压到 14ms，并没有消掉「候选数」这个乘数，batch=16 只是常数级摊销。cross-encoder「每个候选一次完整前向」的本质（ADR-012 设计要点）在 GPU 上依然成立。
3. **拐点在 K≈25**。15→25 用 +0.16s 换 +2.7pt（≈17pt/秒）；25→100 用 +1.0s 只再换 +1.0pt（≈1pt/秒）。中间段（40）AP/MRR 不升反平——深池一边捞回锚点一边带进噪声；K=40 的 Recall 低于 K=25 但复跑稳定，属小样本下 1 个锚点的确定性波动（108 锚点，1 锚点 = 0.93pt）。

**决策**：`RERANK_CANDIDATE_K` 生产默认从 0（=15）改为 **25**（`app/rag/config.py`，仍可由环境变量覆盖）。只作用于 `mode="hybrid_rerank"`；`hybrid`（RRF 对照基线）与 `candidate_pool`（诊断，显式传 `candidate_k`）不受影响。

**放弃的方案**：

1. ~~K = 40 / 60~~——延迟已翻 1.9~2.5×，质量并不优于 K=25。
2. ~~K = 100 拿满 88.0%~~——+3.7pt 但 P50 达 1.67s（3.3×），交互场景代价过高；保留为「质量优先」的可选档。
3. ~~维持 15~~——0.5s 虽最快，但 +0.16s 换 +2.7pt 太便宜，没有理由不拿。

**后续**：继续加候选数不是下一杠杆（收益已见底）。降低精排单候选成本（换更小 reranker / top-N 精排）或转向第二阶段（生成层 Faithfulness / Answer Correctness）优先级更高。

## ADR-014 解析器保留 layout-0.4.0（列网格重建）：接受主指标 −0.9pt，换取文本正确性

**背景**：`docs/pdf-parsing-step9-column-grid.md` 的列网格重建（无框线并列双表阅读顺序）落地后，贝莱德 p16 的文本交错消除（**可验证的文本正确性提升**），但主指标 chunk Rec@5 从 76.5% 掉到 75.6%（−0.9pt）；与此同时 AP/MRR/NDCG 三项**反向上升**。

**归因（决定性证据）**：48 条查询逐条对比，**只有 blk-q4 一条发生变化**，净 −1 fact / −3 gold。原因是 p16 块变干净后主题性显著变强（en 查询里排到第 1，此前第 4），把 p15 上承载 `超配美国股票` / `看好日本股票` 的块挤出了 top-5——**被挤掉的那两页一个字没变**。即 −0.9pt 是 **top-5 只有 5 个槽位**造成的零和竞争，**不是解析质量退化**。

**决策**：**保留 layout-0.4.0**（`TABLE_GRID_ENABLED = True`，`PARSER_VERSION = "layout-0.4.0"`）。

**理由**：

1. 文本正确性是**可验证事实**；指标差是**排序副作用**。前者是确定收益，后者是槽位竞争——同一次「变干净」在别的查询上随时可能反向受益。
2. 放弃的方案——回滚 0.3.0 换回 −0.9pt，代价是**保留一个已知的文本错误**（交错句），且 AP/MRR/NDCG 三项会一起变差。
3. 影响面极小：三重门禁后命中 **4/1244 页**，已入库文档中只有 1 页（贝莱德 p16）。

**整体评测复跑（`app/eval/results/2026-10-11_22.50.28`，五模式全量）**：chunk 级 Rec@5 **75.6%**、候选池召回(gold) **88.5%**，与 0.3.0 时代的 gold 口径基线**完全一致**；增益链 `bm25 38.5% → keyword 37.2% → vector 39.7% → hybrid 50.0% → hybrid_rerank 75.6%` 完整保持。

**回滚路径（保留备用）**：索引 `app/rag/indexes/_backup_layout030/`；代码 `TABLE_GRID_ENABLED = False`。

## ADR-015 生产向量模型切换为 bge-m3，embedding 容器改用 GPU 版 TEI

**背景**：`bge-large-zh-v1.5`（326M，中文优化）是纯中文语料训练的，「中文问题 → 英文文档」这条跨语言路径一直是最弱环。离线的向量单路探针（见 `docs/eval-testset-v3.md` §7.10）给出决定性的数字：换 `bge-m3` 后「中→英」向量层 Rec@5 **33.3% → 66.7%**、候选池 **66.7% → 86.7%**；且该探针对 `bge-large-zh` 的池召回（66.7%）与生产 `hybrid_rerank` 逐位吻合，可信度高。

与此同时暴露出一个此前被低估的事实：**嵌入推理是 CPU 上的真瓶颈**。实测 bge-m3 在 CPU 上约 **1 块/秒**（2367 块 ≈ 40 分钟），与 10-11 那次全量入库（1978 块 / 1796s ≈ 1.10 块/秒）几乎同速 ⇒ 上次入库耗时的大头也在嵌入、而非此前估计的解析。（该错误估计已更正。）

**决策**：

1. **生产向量模型 `bge-large-zh-v1.5` → `bge-m3`**。两者同为 **1024 维**，Qdrant collection 无需变更；bge-m3 是 XLM-RoBERTa 架构，TEI 原生支持。
2. **`embedding` 容器从 `cpu-1.8` 换成 GPU 通用版 tag `1.8`**，并在 compose 里加 `deploy.resources.reservations.devices`（driver nvidia）把 4060 透给容器。**换的是推理引擎镜像、不是模型文件**——bge-m3 权重不动。

**端到端 A/B（仅中文口径，30 查询 / 40 gold 单元，五模式）**：

| 模式 | bge-large-zh Rec@5 | bge-m3 Rec@5 | Δ | 池召回 旧→新 |
|---|---:|---:|---:|---|
| bm25 / keyword（不含向量） | 57.5% / 52.5% | 57.5% / 52.5% | 0 | 不变（对照，证明改动只碰向量路） |
| vector | 57.5% | **75.0%** | **+17.5pt** | 72.5% → 87.5% |
| hybrid | 67.5% | **75.0%** | +7.5pt | 77.5% → 87.5% |
| **hybrid_rerank（生产）** | **85.0%** | **90.0%** | **+5.0pt** | 87.5% → **95.0%** |

分组看，收益**全部落在跨语言**：中→英 `hybrid_rerank` **66.7% → 80.0%**（池 66.7% → 86.7%，与 §7.10 探针的预测**完全一致**）；中→中 `hybrid_rerank` **96.0% 持平**（池 100%）。逐题只 **2 条变化、零回退**：icct-q4（1/2→2/2）、icct-q6（0/2→1/2）。

**理由**：

1. 补的是**结构性短板**（中文向量模型查英文文档），不是刷分；且「中→中」不掉。
2. 成本接近零：维度不变、TEI 原生支持、权重 2.2GB 已离线落盘。
3. 池召回 95% 说明剩余瓶颈已从「召回」转移到「精排排序」——剩余 4 个 miss 中 2 个是池里就没有（召回层）、2 个是池里有但没排进 top-5（排序层），指向明确。

**代价与已知副作用**：

- 模型 326M → 568M，CPU 单次前向更慢；**但换 GPU 后总重编码 2367 块从 ~40 分钟降到 25 秒**（实测 ~139 块/秒，约 130×），代价被完全覆盖。
- ⚠️ **未精排的 `hybrid` 在「中→中」回退 12pt**（88% → 76%）：RRF 只吃名次、丢原始分，向量路变强会改变名次分布，反而扰动融合排序。精排把这块完全救了回来（96% 持平）⇒ **这是 `hybrid_rerank` 必须作为生产模式的新证据**。

**回滚路径**：compose 的 `image` 换回 `cpu-1.8`、`MODEL_ID`/挂载指回 `bge-large-zh-v1.5`（需重新下载 1.3GB，ModelScope 直连约 4 分钟），并用旧模型重跑一次 `reembed_prod.py` 重编码全部向量。

**GPU 环境要点**：Docker Desktop 已注册 `nvidia-container-runtime`；TEI GPU tag 按算力分（`1.8` 通用 / `turing-` / `hopper-`），4060 是 Ada(sm_89) 走通用版。ghcr.io 本机直连不稳，镜像改从 `ghcr.nju.edu.cn` 拉再打回官方 tag。

## ADR-016 精排推理压常数项：按长度排序切批 + fp16 权重（不改检索策略）

**决策**：对精排这一层做两处**不改候选集、不改融合、不改打分语义**的推理侧优化，作为后续
任何检索策略改动前的基线。

1. **按序列长度升序切批**（`reranker._batch_plan`，`RERANK_LENGTH_SORTED` 默认开），
   `RERANK_BATCH_SIZE` 默认 16 → **8**。
2. **fp16 ONNX 权重**（`docker/reranker/export_onnx_fp16.py` 从已有 fp32 ONNX 转换，
   `RERANK_ONNX_SUBDIR=auto` 默认有 fp16 就用、没有静默回落 fp32）。

**背景**：三段耗时拆解显示精排占端到端 P50 的 **74%**（① 召回+RRF 103ms / ② 精排 297ms /
④ 端到端 402ms）。也就是说在此之前，用户等的那 900ms 里有 600ms 花在一个**纯算力常数项**上。
先压它、再谈策略，是因为它的收益归因最干净（不会和召回/融合的改动混在一起）。

**为什么批越小越快（反直觉）**：`_encode` 把一批里所有序列补齐到**该批最长**，而 cross-encoder
是 transformer、单序列注意力 O(L²)——padding 不是免费的。候选池恰好长短混杂（表格块 900+
字符 vs 正文块 200 字符），大批会把短块一起抬长。实测（K=25，25 条真实 chunk，轮转取样 20 次）：

| batch | 原序切批 | 按长度排序切批 | 补齐开销（原序→排序） |
|---:|---:|---:|---|
| 4 | 328ms | **260ms** | 54.0 → 15.8 token/条 |
| 8 | 360ms | 297ms | 61.6 → 34.9 |
| 16 | 444ms | 361ms | 110.0 → 65.9 |
| 25 | 492ms | 487ms | 113.9 → 113.9 |

bs=25（单批，排序无从发挥）**几乎不变**，而 bs≤16 全部受益 17~21% ——「该变的大变、不该变的
不变」即机制自证的内部一致性检验。原先的「单候选 ≈14ms 恒定」其实是**批太大时的 padding 税**，
不是 kernel 成本。

**理由**：两处都只改「同一批怎么拼」和「权重用什么精度」，**理论上不改变任何分数与排名**
（逐对打分与计算顺序无关；降精度只动浮点尾差）。

**代价与验证**（`docs/eval-testset-v3.md` §7.14 / §7.15–7.17）：

- 60 查询、K=25 端到端：**★Rec@5 86.25% 两臂完全相同**；fp32→fp16 逐条对比 **0/60 条变化**。
- 端到端 P50：**909.7ms → 707.5ms（-22%，批处理）→ 402.2ms（-56%，含 fp16）**。
- 五模式全表质量列**逐位不变**；hybrid_rerank 的 AP/MRR/NDCG 微降 0.002~0.003，来源是
  `blk-q2`[zh] 一条在 Top-5 内的位次翻转（浮点尾差让一组接近的分数换了序），
  **没有任何 gold 单元的命中状态改变**——如实记录，不粉饰。
- 候选池深度曲线重测（§7.15）：**K=25 仍是质量拐点**（25→40 的 Rec@5 +0.0pt，代价 +127ms），
  ADR-013 无需修订；K=5 在 43% 的延迟下保留 83.8%，作为交互式场景的性价比拐点。

**已知副作用与边界**：

- fp16 权重是**产物**不是代码：`onnx_fp16/` 不入 git（约 1.06 GiB）。换机器需跑一次
  `python docker/reranker/export_onnx_fp16.py`；没跑也能正常工作（auto 回落 fp32，只慢一倍）。
- 转换脚本必须 `onnx.load(..., load_external_data=True)`（否则转换器读不到权重值，报
  「should be stored in model.onnx_data, but it is not regular file」），且建 session 前要调用
  `Reranker._link_cuda_dlls()`（Windows 上 nvidia-*-cu12 的 DLL 必须落在 `onnxruntime/capi/`）。
- 排序切批只对**长短混杂**的候选池有收益；若将来 chunk 长度被统一（如全部切成固定 400 字符），
  收益会自然消失——届时可关掉 `RERANK_LENGTH_SORTED` 复现对照。

**回滚路径**：`RERANK_ONNX_SUBDIR=onnx`（回 fp32）、`RERANK_BATCH_SIZE=16` +
`RERANK_LENGTH_SORTED=0`（回旧的切批方式）。三者均为独立环境变量，不需要改代码或删文件。

**留给下一步的结论**：并发压测（§7.16）显示这是**吞吐受限**系统——C=8 时吞吐仅 +23%、延迟涨
6.4×，瓶颈是唯一那张 GPU（query embedding 与精排同卡排队）。**并发度换不来吞吐**，因此凡是
「加并发」的方案不必再试；要提吞吐只能降单请求算力成本（更小模型 / 更少候选）。

## ADR-017 非 PDF 文档改走统一结构化解析，不再补默认值

**背景**：`chunker.SUPPORTED_SUFFIXES` 早就声明支持 `.docx` / `.md` / `.txt`，但它们走的是 pypdf 时代的旧提取链路（`extract_document` + `chunk_text`），再由 `ingest._v3_defaults` **补上 schema v3 字段的中性默认值**（`section_path=[]`、`chunk_type` 恒为 `body`、`table=None`、`page_index=None`）。后果是结构信息最清晰的格式拿到了最弱的结果：

- v3 的溯源层（`section_path` / `chunk_type` / `table`）对非 PDF 文档**全部形同虚设**；
- 更严重的是 `_extract_docx` **只遍历 `document.paragraphs`，从不读 `document.tables`** ⇒ Word 文档里的表格内容**整块丢失**——这不是字段缺失，是正文数据丢失；
- 而 docx / md / pptx / html 的结构是**显式标注**的（`paragraph.style.name` 直接给 `Heading N`、`document.tables` 直接给行列、md 的 `#` 数量、html 的 `<h1>` / `<table>`），拿到它们比从 PDF 版面**推断**结构容易一个数量级。让它们走最弱的链路是个倒挂。

**决策**：新增 `app/rag/struct_parser.py`，**两段式**：

1. **适配器**：各格式 → 统一中间表示 `StructBlock`（`kind` ∈ heading/body/table，带 `level` / `rows` / `header_rows`）；
2. **组装器**：`StructBlock` 序列 → schema v3 chunk，与 `pdf_parser` **逐字段对齐**——标题栈 → `section_path`（level 小的压栈、同级或更高级弹栈）、表格独立成块且超长表按行组切、**每块重复表头**、正文走 `split_text` 的句子边界。

用开关 `STRUCT_PARSER`（默认 `struct`）控制，`chunker` 可回退旧链路。同时把 `SUPPORTED_SUFFIXES` 扩到 8 项，纳入 `.pptx` / `.html` / `.htm` / `.markdown`。

**为什么是「统一中间表示」而不是「统一转 Markdown」**：转 md 会把表格压成管道文本、丢掉行列结构；而各格式的表格本来就是结构化的（`document.tables` / `GraphicFrame` / `<table>`），压成文本再解析属于无谓的有损往返。中间表示直接保留 `kind` / `level` / `rows`，一次成型。

**与 PDF 链路的有意差异**（均由"这些格式没有这种东西"决定，不是实现妥协）：`page_index` / `page_label` 恒为 `None`（没有"页"的概念，不冒充页码）、`needs_ocr` 恒为 `False`、`table` 元数据不含 `bbox`（无坐标）、`parser_version` 用 `STRUCT_PARSER_VERSION = "struct-0.1.0"` 与 PDF 的 `layout-*` 区分。

**产物**：`meta.json` 新增 `doc_parsers`（逐文档实际使用的解析器版本）。库级 `parser_version` 只代表 PDF 解析器，混合库（既有 PDF 又有 docx 等）必须看这张表才知道每份文档是谁解析的。

**验证**：五种格式样例全部产出 v3 全字段 chunk（表格不丢、章节层级正确、字段集与 PDF 逐字段一致）；**旧链路对照确认 docx 表格内容确实丢失**；端到端临时库（5 文件 → 13 块）通过；现有 12 份 PDF 仍全部走 `pdf_parser`，生产索引零改动。脚本 `.workbuddy/scripts/test_struct_parser.py`。

**回退路径**：`STRUCT_PARSER=chunker`（不改代码、不删文件）。

## 框架选型

**为什么用 deepagents 而不是：**
- **手写 supervisor**——规划循环、todo 管理、上下文裁剪、子智能体隔离都是成熟轮子；我的价值增量在反思循环、持久化、可观测、安全，而非重复造调度层
- **AutoGen**——对话式多智能体（agent 间聊天）与「主智能体单向调度专家」的模型不匹配，对话轮次不可控
- **CrewAI**——角色固定、流程偏线性，不适合「主智能体按任务动态规划」的 deepsearch 场景
- **纯 LangGraph 手写**——deepagents 本身就是 LangGraph + middleware 的标准化封装（见 `graph.py`），用它等于站在标准结构上做扩展

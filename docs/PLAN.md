# deepsearch-agents 简历项目补齐计划

> 目标：把项目从「deepagents 库的组装 Demo」升级为「基于 deepagents 深度定制」的可防御简历项目。
> 路线：**继续使用 deepagents 框架**，通过读透源码 + 有说服力的定制点（反思循环、持久化、可观测、安全）建立防御深度。
> 周期：3~4 周（2026-10-06 起）。前置认知：第一个项目（电商问数）讲固定编排，本项目必须讲清楚自主性。

---

## 执行顺序（2026-10-03 调整）

实际执行顺序 ≠ 阶段编号顺序。调整原则：先做不依赖框架理解的（安全、持久化、可观测），反思循环边做边读源码，源码精读降级为「按需 + 交付前集中补」。

```text
第 1 周：  阶段五（安全修复，2~3 天，立刻见效）
          → 阶段三（持久化 + 并发，秀后端强项）
第 2 周：  阶段二（反思循环，按需读 deepagents 执行流：graph.py + middleware/subagents.py）
第 3 周：  阶段四（Langfuse + 评测集 + 基线数字）
第 4 周：  阶段一补完（集中源码精读，产出 internals 笔记 + 10 问）
          → 阶段六（测试 + Git + README 收尾）
```

依赖说明：
- 阶段五、三、四与 deepagents 内部机制零耦合，可先行
- 阶段二需要理解框架执行流，但只需读 `graph.py` + `middleware/subagents.py` 两个文件，不必等阶段一完成
- 阶段一**不可删除**：它是面试防御深度的来源，交付前必须补完（internals 笔记是硬产出）

## 项目定位与叙事

简历叙事一句话：

> 基于 deepagents（LangGraph）深度定制的多智能体深度研究系统：主智能体自主拆解任务、反思信息充分性并迭代搜索，整合网络 / MySQL / RAGFlow / 附件四类信源，输出可追踪、可评估的研究报告。

与第一个项目的对照点（面试必讲）：

| 维度 | 电商问数（项目一） | deepsearch-agents（项目二） |
|------|------|------|
| 编排方式 | 固定 workflow，流程写死 | deepagents supervisor 动态规划，路由由模型决策 |
| 自主性 | 无（按图执行） | 规划 → 执行 → 反思 → 补搜迭代 |
| 控制点 | 代码级可控 | 提示词 + 循环终止条件 + 预算约束 |
| 框架角色 | 自己搭的图（自己写） | 深度定制成熟框架（读透源码 + 二次开发） |

**防御策略转变**：不声称「手写规划循环」，而是证明「我对这个框架的理解到了源码级」——面试官追问任何内部机制都能答上来，且定制点都是自己写的。这是更诚实也更可持续的叙事。

## 阶段一：读透 deepagents 源码 + 建立定制基线（按需穿插 + 第 4 周集中补，决定面试防御深度）

**动机**：自主规划能力来自 `create_deep_agent`，面试官追问「task 工具怎么实现的、上下文怎么隔离的」答不上来就露馅。既然选择用框架，就把「读透」做成硬产出，而不是口头声称读过。

**执行方式**：阶段二动手前按需读 `graph.py` + `middleware/subagents.py`；第 4 周集中补完全部精读并产出文档。

### 1a. 源码精读（2~3 天）

- [ ] 通读 deepagents 0.5.7（`.venv/Lib/site-packages/deepagents/`），重点：
  - [ ] `task` 工具实现：子智能体如何被调用、参数结构、结果如何回传主循环
  - [ ] subagent 上下文隔离：消息裁剪策略、共享哪些状态、隔离哪些
  - [ ] planning / todo 机制：提示词怎么驱动规划、todo 状态怎么维护和呈现
  - [ ] 虚拟文件系统：中间产物怎么存、路径怎么约束
  - [ ] checkpointer 如何接入 LangGraph
- [ ] 产出 `docs/deepagents-internals.md`：源码笔记，含一张执行流程图（自己画的，不是抄的）
- [ ] 给自己出 10 个面试问题并写答案（如：子 agent 失败主循环怎么办？todo 列表丢失怎么恢复？）

### 1b. 建立定制基线（第 1 周后半）

- [ ] 提取定制切入点清单：哪些行为可以不 fork 就改（提示词 / 工具包装 / middleware / subagent 结构），哪些必须 fork（写清楚、暂时不做）
- [ ] 把现有三行式 subagent 配置升级为结构化定义（显式声明输入约定、输出 schema、失败重试策略）
- [ ] 每个技术决策写入 `docs/design.md`：为什么选 deepagents 而不是手写 / AutoGen / CrewAI（这段就是面试的「选型」必答题）

**验收**：不看资料能画出 deepagents 执行流程图；`docs/deepagents-internals.md` 完成；10 个自问自答能脱口而出。

## 阶段二：反思循环（第 2 周前半，决定项目上限）

**动机**：deepsearch 的灵魂是「搜了 → 反思够不够 → 不够再搜」。目前只有路由没有反思，与 OpenAI Deep Research 的核心差距就在这。这也是最大的定制点——框架本身不提供，需要自己设计接入。

- [x] 在 deepagents 结构上外层包反思循环（不 fork 框架）：
  - [x] 信息充分性评估节点：汇总当前收集的资料，LLM 判断是否足以回答原问题
  - [x] 缺口驱动补搜：识别缺失维度（时间范围 / 数据来源 / 反方观点），生成针对性补充任务再次进入主循环
  - [x] 终止条件三选一触发：信息充分 / 达到最大迭代轮数（默认 3）/ token 预算耗尽
- [x] 每轮迭代过程推送到前端（复用现有 monitor / WebSocket），展示「反思 → 补搜」的思考链
- [x] 在 `docs/design.md` 写清楚接入方式：为什么这个位置包循环、对框架执行流的影响（ADR-001/002/003）
- [ ] 真机验证：用一个开放研究型问题跑通「至少一次反思补搜」，录制 Demo（需配置真实 API Key）

**验收**：录一段 Demo，同一个问题能看到至少一次「反思 → 补搜」迭代；极端问题（信息不可得）能正确终止而非死循环；能讲清楚「这个循环是框架没有、我加的」。

## 阶段三：持久化与并发（第 2 周后半，秀后端强项）

- [ ] `InMemorySaver` → `AsyncPostgresSaver`（docker-compose 加 Postgres 服务）
- [ ] `active_tasks` 内存 dict → 表登记或 Redis，支持多 worker 部署
- [ ] uvicorn 多 worker 验证：两个会话并发执行互不干扰
- [ ] 任务异常恢复：服务重启后 unfinished 任务状态可查询（不要求续跑，状态可见即可）

**验收**：重启服务后会话历史不丢；压测脚本 10 并发任务无串目录、无崩溃。

## 阶段四：可观测性与评估（第 3 周，面试数据弹药）

- [ ] 接入 Langfuse（自部署或云版）：每次任务的完整 trace、token 成本、延迟
- [ ] print 全部替换为 logging（结构化 JSON 日志）
- [ ] 构建评测集：20 条任务（网络类 / 数据库类 / 知识库类 / 混合类各 5 条）
- [ ] 定义指标并跑出基线数字：任务成功率、平均工具调用次数、平均迭代轮数、平均 token 成本
- [ ] 反思循环前后对比数据（如：成功率 65% → 85%），这是简历上最硬的一句话

**验收**：`docs/eval.md` 有完整指标表格；简历可写「通过反思循环将任务成功率从 A 提升到 B」。

## 阶段五：安全加固（穿插进行，低成本高回报）

- [ ] **修复上传路径穿越**：`upload_files` 中 `file.filename` 直接拼接，`../../` 可逃逸目录 → 文件名消毒（`Path(filename).name` + 白名单后缀 + 大小限制）
- [ ] 下载 / 列表接口改造：前端不再传绝对路径，改为 `session_id + filename`，服务端自行拼接待删除
- [ ] CORS 收紧：`allow_origins` 改为显式白名单，去掉 `*` + `credentials` 组合
- [ ] SQL 工具兜底：`execute_sql_query` 确认只读（或强制 `LIMIT` + 只读账号），写入 `docs/security.md`
- [ ] `app/updated/`、会话产物清理策略（定期归档或删除过期 session）

**验收**：`docs/security.md` 记录漏洞 → 修复对照，面试可讲「发现并修复了自己项目的 N 个安全问题」。

## 阶段六：测试、Git 历史与 README（第 4 周，收尾）

- [ ] 后端测试：路径穿越、下载越权、任务取消、会话隔离（pytest，目标核心路径覆盖）
- [ ] git 历史整理：当前只有 1 个 Initial commit；后续按阶段正常提交，形成可读的演进史
- [ ] README 重写（面试官第一眼）：
  - [ ] 架构图（deepagents 执行流 + 我的反思循环扩展，用 Mermaid 或 draw.io）
  - [ ] 「对 deepagents 的定制点」一节（反思循环、结构化 subagent、持久化——哪些是框架的、哪些是我加的，边界清晰）
  - [ ] 量化指标表（来自阶段四）
  - [ ] 技术决策记录（ADR 风格，3~5 条，含框架选型对比）
  - [ ] 5 分钟快速启动（docker compose 一键起）
- [ ] 录制 2 分钟 Demo GIF 放 README 首屏

**验收**：一个陌生 clone 后 `docker compose up` + 配 `.env` 即可跑通；简历项目链接点开 30 秒内能看懂这是什么、亮点在哪。

## 里程碑与风险

| 时间 | 里程碑 | 不可妥协产出 |
|------|------|------|
| 第 1 周末 | 安全修复 + 持久化上线 | `docs/security.md` + 重启不丢状态 |
| 第 2 周末 | 反思循环跑通 | Demo 有迭代过程 |
| 第 3 周末 | 评测报告出炉 | 有前后对比数字 |
| 第 4 周末 | 可交付 | `docs/deepagents-internals.md` + README + 测试齐 |

**风险**：
1. 源码精读压到最后被挤掉 → 保护措施：阶段二动手时强制先读两个核心文件；internals 笔记列入第 4 周不可妥协产出
2. 反思循环在 deepagents 外层包不动（框架耦合） → 兜底：fork 提示词或子智能体层级实现，`docs/design.md` 记录放弃的路线及原因（失败路线也是面试谈资）
3. 评测成功率数字不好看 → 诚实呈现 + 归因分析，面试价值反而更高
4. 时间不够 → 优先级：阶段五 > 三 > 二 > 四 > 一 > 六（阶段六的 README 重写不可省，测试可缩范围）

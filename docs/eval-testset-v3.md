# 检索测试集改版（v3）：锚点重校 + chunk 级 gold

> 2026-10-11。本次做两件事：**① 把 67 个锚点对 v3 索引逐个重校**；**② 给每道可跑题补 chunk 级 gold，把主指标从 fact 级 micro Recall@5 换成 chunk 级 gold Recall@5 / AP@5 / MRR@5 / NDCG@5**。
> 产物：`app/eval/calibrate_retrieval.py`（校准工具）、`app/eval/build_gold.py`（gold 生成/校验）、`app/eval/retrieval-tasks.yaml`（题库 + `gold` 字段）、`app/eval/eval_retrieval.py`（主指标改造）。

---

## 0. 一页结论

| 项 | 改前 | 改后 |
|---|---|---|
| 锚点有效率（可跑 48 个） | FAIL-0 **2** 个（0 命中） | FAIL-0 **0** |
| 相关块判定 | 「含任一锚点即相关」（近似） | **chunk 级 gold 真值**（content_hash） |
| 主指标 | fact 级 micro Recall@5 | **chunk 级 gold Recall@5 / AP@5 / MRR@5 / NDCG@5** |
| 评测口径 | 随切块粒度漂移、跨版本不可比 | 以「标准答案的出处」为分母，语义稳定 |
| 全量 16 题结果（hybrid_rerank） | fact Rec@5 81.5%（口径已变） | **chunk Rec@5 63.2%** / AP .747 / MRR .739 / NDCG .803 |

**为什么要换主指标**：fact 级 micro Recall@5 的分母是「该题 fact 数」、命中靠子串包含，**切块粒度一变数字整体漂移**。v2（400 字滑窗 + 80 字重叠）→ v3（按节切块 + 表格独立成块）同题同锚点从 87.0% 掉到 79.6%，其中相当一部分是**粒度差异**（v2 相邻块重叠让同一事实在多块重复出现、命中被重复计数）而非检索质量差异。gold 口径以「标准答案的出处」为分母，不受「一个事实被切成几块」影响。

## 1. ① 锚点重校

### 1.1 工具：`app/eval/calibrate_retrieval.py`

题库头部「锚点校准铁律 #5」的自动化版本。对每个 pattern 统计**当前索引**里的命中 chunk 数与占比（分母 = 库内 chunk 总数），打四类标：

| 标记 | 含义 |
|---|---|
| `FAIL-0` | 0 命中 —— 锚点在库里找不到（切块/解析变更后失配，或写错） |
| `WARN-BROAD` | 占比 > 3% —— 锚点过泛，会把大量无关块判成相关 |
| `WARN-CROSS` | 命中了非答案文档 —— 同库跨文档假阳性 |
| `WARN-SPACE` | 原文 0 命中但「压掉空白后」能命中 —— 撞上 PDF 双空格 |

```
python -m app.eval.calibrate_retrieval [--write]
```

## 2. ② chunk 级 gold

### 2.1 设计

- 每道可跑题在 `facts` 之外新增 `gold` 字段：**该题标准答案应落在哪些 chunk 上**。
- 主键 = **`content_hash`**（schema v3 字段，随 chunk 文本稳定），而不是 `seq`（jsonl 行号，重切块必变）。选 hash 是为了让「重切块后 gold 失效」**显式暴露**，而不是悄悄算出一堆错的数。
- 生成/校验工具：

```
python -m app.eval.build_gold          # 打印可直接粘贴回题库的 gold 块
python -m app.eval.build_gold --check  # 校验题库已有 gold 是否与当前索引一致
```

`--check` 会报「失效 = hash 不在当前索引」与「新增 = 当前应命中但题库里没有」；`失效 > 0` 即 **gold 需要重标**。

### 2.2 规模

| 项 | 值 |
|---|---|
| 题库总量 | 21 题 / 67 锚点 |
| 可跑（文档已入库） | **16 题 / 45 锚点** |
| gold chunk | **39 个**（ICCT 20 / 贝莱德 19） |
| 每题 gold 数 | 1 ~ 5（平均 2.4） |
| 校验结果 | 16/16 有效（失效 0、新增 0） |

### 2.3 口径变更（`eval_retrieval.py`）

- **相关块判定**：有 gold → 查 `content_hash ∈ gold`（真值）；无 gold → 回落「含任一锚点」近似，报告头会打印 `⚠ 无 chunk 级 gold 的题`。
- **★chunk Rec@5（新主指标）** = Top-5 覆盖的 gold chunk 数 / 该题 gold 总数，汇总用 micro（Σ命中 / Σgold）。
- ★Prec@5(AP@5) / ★MRR@5 / NDCG@5 / 占比@5：相关块一律由 gold 定义（原为锚点近似）。
- **fact 级 micro Rec@5 降为参考列**，表头标 `(参考)`，脚注写明「跨切块版本不可比」。
- 候选池召回同步给 gold 口径（`池召回(gold)`），它就是 chunk Rec@5 的理论上限；fact 口径的池召回退到报告脚注。
- 诊断列（`--diag`）同时给 gold / fact 两口径的 Recall@20。

## 4. 已知缺口：p16「战术配置细分观点」的无框线 3 列表

`blk-q4` 两条锚点失效暴露出的**解析层真实缺陷**，记录如下（正是 Plan C3 点名的「无框线表要单独测」）：

- **现象**：贝莱德 p16 是一张 3 列（资产 / 观点 / 评论）**无框线表**。`find_tables(strategy="lines")` 只抓到 **2 行表头**（chunk `88d28c39ec2fe35b`，2×3），表体没被识别成表，而是被读成**列间交错的正文流**。
- **后果**：行标签被拆开（`长期投资级别` + `信用债` 分落两处），观点与评论交织（`我们持中性观点。中国债券可提供稳定性与分散投资价值`）。**该页的「资产 → 观点」映射无法从索引里可靠读出**。
- **影响面**：仅 p16 一页（其余 p3/p9/p11/p15 的锚点均正常命中）。
- **处置**：本次**只改测试集**（改用原文里真实存在的连续串重锚），未改解析器。后续若要恢复该页的表格语义，需在自研解析器里给无框线多列区域补「按列切分 + 列内顺序」的兜底（属解析层后续工作，不在本次范围）。

## 6. 局限与维护约定

1. **gold 需要人工标注**，且**换解析器 / 改切块参数后必须重标**——`build_gold --check` 会在 hash 失效时立刻报警。这是换取「跨版本可比」的成本。
2. **39 个 gold 是按当前 `PARSER_VERSION=layout-0.3.0` 标的**；一旦解析器升级导致文本变化，先跑 `--check` 再决定是否重标。
3. `kb-06 ~ kb-10`（22 锚点）仍锚在未入库文档上、未校准，评测自动跳过、不计入任何指标。
4. 3% 的「过泛」阈值是为 310 chunk 的 ICCT 库定的；小库（如 79 chunk 的贝莱德）同一绝对命中数会天然超线，需按库规模解释（见 §1.4）。
5. 主指标只覆盖**检索层**；生成层的 Faithfulness / Answer Correctness 属第二阶段（见 `app/eval/eval.md`）。

### 7.6 发现：gold「最小覆盖集」的**等价块假 miss**

以 kb-18（斯坦福·AI 事故 362 / 233 起）为典型：

| 块 | 页码 | 文本 | 角色 |
|---|---|---|---|
| `c80793d3aa64a73b` | p10 执行摘要 | 「记录在案的人工智能事故数量升至 362 起，高于 2024 年的 233 起」 | **gold** |
| `6bae8c2f7f2ab7d2` | p128 章节正文 | 「人工智能事件数据库在 2025 年记录了 362 起事件，高于 2024 年的 233 起」 | 等价块（**非 gold**） |

实测 `kb-18/zh: gold 0/1 | fact 2/2` —— 检索命中了 **p128 等价块**（fact 全中），却因不在 gold 集合判 miss。
本次 hybrid_rerank 共 **2 条**此类（`kb-18/zh`、`kb-22/en`）。

- **根因**：`build_gold` 的「最小覆盖集」在**同一事实被多块等价覆盖**时只保留一个块，命中其余等价块被误判。

### 7.8 gold 等价组修正（同日 18:08）

**改法（答案单元）**：`gold` 的每个元素从「一个 hash」升级为「一个单元」——单块单元直接写
`"hash"`，等价块单元写 `["h1","h2"]`（**命中任一即算该单元命中**），单元之间才是 AND。
`Rec` 的分母 = **单元数**（不是块数）。这样处理的两个理由：

- 若把等价块**平铺并入** gold，命中一个只算 `1/2`，反而把「答案已完整找到」判成半对——语义错；
- 等价关系**固化在题库里**（可审查、跨版本可比），不引入运行时的锚点近似。

**自动检测**：`build_gold` 生成时，若最小覆盖集是**单块**且存在**其他能独立覆盖全锚点的块**，
即合并为一个 OR 单元。全库命中 **5 题**：

### 7.10 向量模型 A/B 探针：`bge-large-zh-v1.5` vs `bge-m3`（2026-10-12，**离线、向量单路**）

**动因**：§7.9 显示中文口径下「中→英」是最弱一环（66.7%），而该方向的池召回只有 66.7%
（miss 全在召回层）；且中文 query × 纯英文库时**关键词路被语言路由主动禁用**（ADR-010）⇒
「中→英」实际是**向量单路**，向量模型就是这条线的天花板。

**方法**（`.workbuddy/scripts/embed_model_probe.py`，**不碰生产索引**）：本地 `transformers`
把同一批 chunk（4 篇 2367 块，`MAX_CHARS=480` 与生产 `EMBEDDING_MAX_CHARS` 一致）与同一批
30 条中文查询各编码一遍，两模型走**完全相同的数学**（CLS pooling + L2 归一化），
同一套 gold 单元判定，池=top-25。控制变量，纯本地 CPU 推理（venv torch 为 `2.14.1+cpu`，耗时 39min）。

| 分组 | bge-large-zh-v1.5 Rec@5 | bge-m3 Rec@5 | Δ | bge-large-zh 池@25 | bge-m3 池@25 | Δ |
|---|---:|---:|---:|---:|---:|---:|
| **全部（30 查询）** | 57.5% (23/40) | **72.5%** (29/40) | **+15.0pt** | 80.0% (32/40) | **92.5%** (37/40) | +12.5pt |
| 中→中（20 查询） | 72.0% (18/25) | **76.0%** (19/25) | +4.0pt | 88.0% (22/25) | **96.0%** (24/25) | +8.0pt |
| **中→英（10 查询，ICCT）** | 33.3% (5/15) | **66.7%** (10/15) | **+33.4pt** | 66.7% (10/15) | **86.7%** (13/15) | **+20.0pt** |

**ICCT 逐题（中→英）**：bge-m3 在 q5/q8（0→1）、q6（0/2→**2/2**）、q7（1/2→2/2）、q9（0→1）胜；
q4 池 1/2→**2/2** 但 top-5 仍 0/2（多目标查询，属精排问题）；**唯一回退** q3（1/2→0/2）。

**探针可信度校验**：bge-large-zh 的「中→英」池@25 = **66.7%**，与 §7.9 生产 `hybrid_rerank`
的「中→英」池召回 **66.7%** 逐位吻合 ⇒ 探针忠实复现了生产的向量路行为（「中→英」在
hybrid 中退化为此单路）。

**结论**：
1. **换 bge-m3 对「中→英」是数量级改善**：向量层 Rec@5 33.3%→66.7%（翻倍）、池 66.7%→86.7%。
   由于精排**只重排不增删**，池上限抬高 ⇒ 端到端「中→英」的**上限从 66.7% 抬到 ~86.7%**。
2. **「中→中」也小幅变好**（72.0→76.0，池 88.0→96.0），没有变坏的方向。
3. **迁移成本低**：bge-m3 同为 **1024 维**（Qdrant collection 维度不变）、XLM-RoBERTa 架构
   （TEI 原生支持，`docker/embedding` 换个目录即可）；代价是模型 326M→568M（编码更慢）。
4. **注意**：本探针是**向量单路**，不是端到端；生产还有关键词路（中→中）与精排。要拿「换模型后
   五模式的真实数字」需跑**端到端 A/B**：起 bge-m3 的 TEI → 摄入到 `kb__m3` 后缀旁路索引
   （复用 `RAG_KB_SUFFIX`；**chunk 不变 ⇒ content_hash 不变 ⇒ gold 仍然有效**）→ 跑五模式对比。

**产物**：权重 `.workbuddy/models/bge-m3/`（2.2GB，sha256 与 HF 官方 etag 一致）；探针脚本
`.workbuddy/scripts/embed_model_probe.py`。

### 7.11 端到端 A/B：生产向量模型切换为 bge-m3（2026-10-12，**仅中文口径**，权威）

**执行方式**（比原计划的旁路库更简）：

- **不重新解析、不旁路**。4 篇文档的 `chunks.jsonl` 已存在且解析器未变 ⇒ chunk 文本逐字节相同 ⇒ **只重编码**与 `--force` 全量重入等价，且不会把知识库目录下另外 8 份非基准 PDF 卷进来。

mixed 比 zh 低 7.5pt 但池召回同为 95% ⇒ gap 全在**排序层**（中英混排让精排难排），不在召回层。

### 7.13 阶段诊断能力：逐 gold 块定位 miss 发生在哪一层（2026-10-12 晚）

**动机**：§7.11 只能看到「池召回 95%、chunk Rec@5 86.2%」这类聚合数字，无法回答「某个 miss
到底是没召回、还是融合排名低、还是被精排挤掉」。为此新增一套**只读**的阶段诊断能力（不是
检索策略改造）。

**实现**（观测能力建设，`trace=False` 时行为与历史完全一致）：

- `retriever._fused_ranking(..., trace=True)` / `search_with_pool(..., trace=True)`：在**同一次
  真实检索**中额外返回中间排名快照——`vector_seqs`（向量腿）/ `keyword_seqs`（关键词腿）/
  `rrf_seqs`（精排前）/ `rerank_seqs`（精排后），外加 `keyword_status`。**不额外发起检索**、
  不改变排序与截断。`trace=False` 返回值与历史逐位一致（二元组）。
- `eval_retrieval`：`--diag` 输出逐条明细的逐 gold 块排名；`--diag-table` 输出「一行 = 题 ×
  查询语言」的阶段诊断表 + 2×2（查询语言 × 文档语言）阶段分布。
- 逐 gold 块**独立记录**（不取最小排名），块级排名与单元级 Rec@5 并存、分母不变。

**三个新字段含义**：

| 字段 | 含义 |
|---|---|
| `vector_rank` / `keyword_rank` / `rrf_rank` / `rerank_rank` | 该 gold 块在四阶段的独立排名；`-` = 未出现在该阶段 |
| `in_pool` | 是否进入候选池（精排前的融合集合） |
| `keyword_status` | `found` / `searched_not_found` / `skipped_by_router`——区分「语言路由跳过」与「跑了没召回」 |
| `top5_distractors` | 最终 Top-5 中排在首个正确块之前的非相关块（含 hash/seq/doc） |

**阶段归因**（自动分类每个 gold 块）：

- **A 未进候选池（召回层）**：两路都没召回到 → 真实召回失败（**与精排无关**）。
- **B 池内但融合排名>5**：在池内，RRF 排名本就靠后 → 融合/单路排序层。
- **C RRF在5内但被精排挤出**：上一阶段（RRF）排名 ≤5，却被精排挤出 Top-5 → **精排的真实失误**。

**结果（2026-10-12 22:09，60 查询 / 90 gold 块；报告 `..._22.09.53_...md`）**：

五模式主指标与 §7.12 基线**逐位一致**（86.2% / 池 95.0%）⇒ trace 零副作用。

| 阶段 | gold 块数 | 占比 |
|---|---:|---:|
| 命中@5 | 75 | 83.3% |
| **A 未进候选池（召回层）** | **7** | 7.8% |
| **B 池内但融合排名>5** | **6** | 6.7% |
| **C RRF在5内被精排挤出** | **2** | 2.2% |

`keyword_status`：`found=50`、`skipped_by_router=10`（10 条中文×英文文档查询被语言路由禁用关键词路）。

**按「查询语言 × 文档语言」阶段分布（2×2）**：

| | 中文文档（同语言） | 英文文档（跨语言） |
|---|---|---|
| **中文 Query** | n=29：命中 27、B 2 | n=16：命中 12、**A 3**、C 1 |
| **混合 Query** | n=29：命中 25、A 1、B 2、C 1 | n=16：命中 11、**A 3**、B 2 |

**结论（对「改哪里」的直接指引）**：

1. **不能把剩余 miss 全甩给精排**：排序层 miss 共 8 块，其中精排造成的（C）只有 **2 块**；
   另外 6 块（B）在 RRF 阶段排名就已 >5 —— 精排反而在改善它们（如 blk-q3：RRF 24 → 精排 8）。
2. **召回层失败（A）几乎全在英文文档**：6/7 出现在「×英文文档」两格 ⇒ 跨语言（中→英）**召回**
   仍是短板（bge-m3 已大幅改善，但未清零），不该归因精排。
3. **精排的两个明确失误靶子**（情况 C）：
   - `icct-q6` [zh]：gold 块 `e35cf681211ab533` RRF 排 **5** → 精排推到 **7**。
   - `blk-q4` [mixed]：gold 块 `1ea846375cb99492` RRF 排 **1** → 精排推到 **6**（把融合第一名踢出）。
4. **`blk-q3` 不是精排问题**：gold 块 `8d9c4dc252b60327` RRF 排 24 / 33（zh / mixed），精排升到 8
   —— 属**融合排序层**（B），修正了「池满分缺 top-5 ⇒ 精排」的先前猜测。
5. **mixed 失败样本规律**：混合查询在**中文文档**上偏 B（融合排名，如 blk-q1/blk-q3/blk-q4），
   在**英文文档**上偏 A（召回，如 icct-q4/icct-q6/icct-q9 的 mixed 臂）⇒ mixed 的短板不在精排，
   而在「融合排序」与「跨语言召回」。

**不在本次范围**：不改 RRF 权重、不改精排输入、不改候选池深度（避免收益来源混淆）。

复现：`python -m app.eval.eval_retrieval --diag-table`（=`--diag` 阶段列 + 诊断表）；`--diag`
单跑则输出逐条明细的逐块排名。

### 7.14 精排推理优化：批内 padding 与 fp16 权重（2026-10-13）

**背景**：§7.16 的三段耗时拆解显示精排占端到端 P50 的 **84%**。在动任何检索策略之前，
先把这一层的**常数项**压掉——它不改召回集、不改融合、不改排序逻辑，风险最低。

#### 7.14.1 它本来就是批量推理，但批不该那么大、更不该不排序

`Reranker.rerank()` 一直是批量：候选编码后按 `RERANK_BATCH_SIZE` 切批，**每批一次
`session.run`（矩阵前向）**，不是 Python 循环逐篇调用。问题出在批**过大**且**未排序**。

`app/eval/bench_rerank.py`（25 条真实 chunk、固定查询、轮转取样 20 次、RTX 4060 Laptop、CUDA EP）：

| batch | 原序切批 | 按长度排序切批 | 补齐开销（原序 → 排序） |
|---:|---:|---:|---|
| 4 | 328ms | **260ms** | 54.0 → 15.8 token/条 |
| 8 | 360ms | 297ms | 61.6 → 34.9 |
| 16 | 444ms | 361ms | 110.0 → 65.9 |
| 25 | 492ms | 487ms | 113.9 → 113.9 |
| 32 | 493ms | — | — |

两个反直觉但可复现的结论（嵌套循环与轮转取样两轮独立测量一致，排除了 GPU 热/功耗的顺序效应）：

1. **批越小越快**：bs=25 比 bs=4 慢 **1.5×**，与「大批更省 kernel launch」的直觉相反。
2. **按长度升序切批再快 17~21%**（bs≤16）；而 bs=25（单批，排序无从发挥）**几乎不变**
   （492 → 487ms）——「该变的大变、不该变的不变」正是机制自证的内部一致性检验。

**机制 = padding 浪费**：`_encode` 把一批里所有序列补齐到**该批最长**，而 cross-encoder 是
transformer，单序列注意力 O(L²)，padding 不是免费的。候选池恰好长短混杂（表格块 900+ 字符
vs 正文块 200 字符），大批会把短块一起抬到 260 token。上表「补齐开销」列（每条序列多算的
token 槽位）与耗时同向变化，即为证据。

**改动**：`reranker._batch_plan()` —— 先按序列长度升序排，再按 `RERANK_BATCH_SIZE` 切批；
`RERANK_BATCH_SIZE` 默认 16 → **8**；新增 `RERANK_LENGTH_SORTED`（默认 1，置 0 复现对照臂）。
排序**不改变任何分数与排名**（逐对打分，与计算顺序无关），只换同批邻居。

#### 7.14.2 fp16 权重：精排再快一倍，指标一字不变

`docker/reranker/export_onnx_fp16.py` 用 ORT 自带的
`onnxruntime.transformers.float16.convert_float_to_float16(..., keep_io_types=True)`
在**已有 fp32 ONNX 上**做权重降精度——图结构不变、输入输出仍是 fp32，调用侧零改动。
（`optimum-cli` 没有 fp16 开关，重导还得重跑一遍图优化，不划算。）

- 体积：**2.27GB → 1.06 GiB**（正好一半）
- 数值：3 条样本 logits 最大绝对差 **0.00566**（阈值 0.02），排序一致
- 默认 `RERANK_ONNX_SUBDIR=auto`：有 `onnx_fp16/` 就用它，没有则**静默回退 fp32**
  （不会因为缺文件把精排整条降级掉）；报告里记录实际用的是哪份权重

#### 7.14.3 端到端验证（60 查询，每路候选 K=25）

| 配置 | ★Rec@5 | NDCG@5 | AP@5 | MRR@5 | ② 精排 P50 | ④ 端到端 P50 |
|---|---:|---:|---:|---:|---:|---:|
| 基线：bs=16、未排序、fp32（2026-10-12 22:09） | 86.25% | 0.8471 | 0.7900 | 0.8000 | — | 909.7ms |
| bs=8 + 按长度排序，fp32 | 86.25% | 0.8450 | 0.7872 | 0.7972 | 592ms | 707.5ms |
| bs=8 + 按长度排序 + **fp16** | **86.25%** | **0.8450** | 0.7872 | 0.7972 | **295ms** | **402.2ms** |

- **主指标 ★Rec@5 两臂完全相同**；fp32 → fp16 的逐条对比 **60 条查询 0 条变化**（含 Top-5
  来源文档集合）。五模式全表（§7.17）同样逐位不变。
- 批处理那一档使 NDCG/MRR/AP 各微降 0.002~0.003：来源是 `blk-q2`[zh] 一条在 Top-5 内发生了
  位次翻转（padding 宽度变化带来的浮点尾差让一组接近的分数换了序），gold 命中数不变。
  **这是 1/60 的位次抖动，不是质量回退**，但如实记录。
- 端到端 P50：909.7ms → 707.5ms（**-22%**，批处理）→ **402.2ms（-56%**，再加 fp16）。

**两处改动都是「零风险」性质**：不改候选集、不改融合、不改精排的打分语义，只改「同一批
怎么拼」和「权重用什么精度」。这也是本项目的取舍原则——**先把常数项压掉，再谈策略**。

复现：

```bash

python -m app.eval.bench_rerank --ks 25 --batches 4,8,16,25 --reps 20 --no-sort   # 排序对照臂
python docker/reranker/export_onnx_fp16.py --check                                # fp16 数值对比
RERANK_ONNX_SUBDIR=onnx python -m app.eval.eval_retrieval --mode hybrid_rerank    # fp32 臂
python -m app.eval.eval_retrieval --mode hybrid_rerank                            # fp16 臂（auto）
```

### 7.15 候选池深度扫描：质量拐点仍在 K=25，性价比拐点在 K=5（2026-10-13）

**动机**：ADR-013 把每路候选深度定为 25，依据是「15→25 用 +0.16s 换 +2.7pt」。§7.14 把
精排单候选成本压到原来的约 1/3 之后，这条曲线的拐点可能移动，必须重测。

固定 60 查询（30 题 × zh/mixed），仅跑 `hybrid_rerank`，`--rerank-k` 逐档覆盖
（fp16 臂报告：`app/eval/results/2026-10-13_20.58.40 ~ 21.00.25__retrieval__hybrid_rerank.*`）：

| 每路候选 K | ★Rec@5 | NDCG@5 | AP@5 | 池召回 | 池−Rec@5 | ① 召回+RRF P50 | ② 精排 P50 | ④ 端到端 P50 | P95 | max |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 5 | 83.8% | 0.796 | 0.747 | 83.8% | +0.0 | 102ms | 69ms | **171ms** | 212ms | 385ms |
| 10 | 81.2% | 0.792 | 0.743 | 85.0% | +3.7 | 103ms | 130ms | 235ms | 286ms | 325ms |
| 15 | 83.8% | 0.838 | 0.784 | 90.0% | +6.2 | 100ms | 188ms | 295ms | 341ms | 355ms |
| **25** | **86.2%** | **0.845** | 0.787 | 95.0% | +8.7 | 103ms | 297ms | 402ms | 483ms | 554ms |
| 40 | 86.2% | 0.847 | 0.790 | 95.0% | +8.7 | 102ms | 427ms | 529ms | 688ms | 700ms |

**四条结论**：

1. **质量拐点仍是 K=25**：25 → 40 的 ★Rec@5 **+0.0pt**（NDCG 仅 +0.002），代价 +127ms（+32%）。
   ADR-013 的 K=25 在当前配置下**依然成立**，且**不需要**因为精排变快而上调——瓶颈已经不在

### 7.16 三段耗时拆解与并发压测（2026-10-13）

**动机**：单线程 P50 只说明「一个人用起来多快」。要回答「这 400ms 花在哪」以及「同时来 8 个
请求会怎样」，必须把链路拆开、并在并发下重测。

#### 7.16.1 三段独立计时

`retriever._fused_ranking(trace=True)` 在**同一次真实检索**内记录耗时（不额外检索；
`trace=False` 时只多两次 `perf_counter`，返回值与行为一字未改），`--timing` 把它写进报告：

| 段 | 覆盖范围 | K=25 fp16 P50 | P95 | max |
|---|---|---:|---:|---:|
| ① 召回 + RRF 融合 | query embedding（HTTP 到 TEI）+ ES 关键词路 + RRF | 103ms | 140ms | 149ms |
| ② 精排单独推理 | 候选编码 + ONNX `session.run` | 297ms | 364ms | 460ms |
| ③ 检索层合计 | ① + ② + 结果整理 | 402ms | 483ms | 554ms |
| ④ 端到端 | ③ + `_materialize`（取原文、构造字典） | 402ms | 483ms | 554ms |

③ 与 ④ 相等 ⇒ 热缓存下 `_materialize` 可忽略（索引常驻内存）。**① 占 26%、② 占 74%** ——
这也解释了为什么 §7.14 的优化直接把端到端砍掉一半。

⚠️ **分位数不可加**：① 的 P50 + ② 的 P50 不会精确等于 ③ 的 P50（不是同一批查询的同一分位），
报告里只作粗略占比看。

#### 7.16.2 并发压测

`app/eval/bench_concurrency.py`（60 条真实查询/轮、线程池并发、索引与精排已预热，
`--json .workbuddy/scripts/out/bench_concurrency_fp16.json`）：

| 并发 | 墙钟 | 吞吐 QPS | P50 | P95 | max | 吞吐加速 | 延迟劣化 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 23.8s | **2.5** | 406ms | 482ms | 1498ms | 1.00× | 1.00× |
| 2 | 18.5s | 3.2 | 675ms | 788ms | 821ms | 1.28× | 1.66× |
| 4 | 18.6s | 3.2 | 1325ms | 1651ms | 1849ms | 1.28× | 3.27× |
| 8 | 19.3s | 3.1 | 2606ms | 3361ms | 4002ms | 1.23× | 6.42× |

**结论：并发不提升吞吐，只堆延迟**（C=8 吞吐仅 +23%，而延迟涨 6.4×）。瓶颈是**唯一那张
GPU**——query embedding（TEI 里的 bge-m3）与精排（进程内的 bge-reranker-v2-m3）在同一张
4060 上排队；ES、HTTP、对象构造这些 CPU 侧工作根本不是限制。C=1 → C=2 那 28% 的增益来自
「一条请求等 GPU 时另一条去查 ES / 走网络」，再往上就没了。

对照（同一脚本、fp32 权重、改动前）：单并发吞吐 1.5 QPS、C=8 时 1.6 QPS ⇒ **fp16 把单并发
吞吐抬了 67%（1.5 → 2.5），但与并发的扩展性形态完全相同**。这说明：

- 这是**吞吐受限**而非延迟受限的系统：降单请求算力成本能直接换吞吐，**并发度换不来**。
- 交互式（人在等）→ 并发控制在 2~4；批处理（离线评测/批量问答）→ 串行反而总时间最短。
- 要真正提吞吐只有三条路：更强 GPU、更小的精排模型、或减少精排候选数（§7.15：K=5 把 ②
  从 297ms 降到 69ms ⇒ 单并发吞吐可再翻倍）。

复现：

```bash

python -m app.eval.eval_retrieval --mode hybrid_rerank --timing --rerank-k 15      # 换 K 重跑
python -m app.eval.bench_concurrency --mode hybrid_rerank --concurrency 1,2,4,8    # 并发
```
